# 1. What we have at the end of Chapter 5

Before changing anything, it is worth making the starting point explicit.

At the end of Chapter 5, the important part of the renderer is approximately this:

```cpp
struct Bounds {
    glm::vec3 origin;
    float sphereRadius;
    glm::vec3 extents;
};

struct RenderObject {
    uint32_t indexCount;
    uint32_t firstIndex;
    VkBuffer indexBuffer;

    MaterialInstance* material;
    Bounds bounds;
    glm::mat4 transform;
    VkDeviceAddress vertexBufferAddress;
};

struct DrawContext {
    std::vector<RenderObject> OpaqueSurfaces;
    std::vector<RenderObject> TransparentSurfaces;
};
```

`MeshNode::Draw()` walks the GLTF node tree and creates `RenderObject`s.

The renderer then roughly does this:

```text
GLTF scene graph
      |
      v
MeshNode::Draw()
      |
      v
DrawContext
      |
      +---- OpaqueSurfaces
      |
      +---- TransparentSurfaces
      |
      v
CPU frustum culling
      |
      v
CPU sorting
      |
      v
for every RenderObject
    bind material if changed
    bind index buffer if changed
    push transform + vertex address
    vkCmdDrawIndexed()
```

This is already a fairly good small renderer.

The important limitation is not that `vkCmdDrawIndexed()` is inherently slow. The limitation is that the **CPU is still responsible for every object**.

Even after Chapter 5's sorting and culling, the CPU still decides:

- whether an object is visible;
- which mesh it uses;
- which material it uses;
- which index buffer must be bound;
- which transform must be pushed;
- when to issue each draw.

Our goal is to make the CPU stop doing most of that for opaque geometry.

## Keep Chapter 5 working

We are going to keep the existing renderer available while building the new one.

This matters a lot.

GPU-driven rendering changes several systems at once. If we delete the old draw path immediately and the screen becomes black, there are too many possible causes:

- indirect command layout;
- descriptor indexing;
- Buffer Device Address;
- object IDs;
- mesh IDs;
- material IDs;
- index offsets;
- compute synchronization;
- culling math.

Instead we will make each step render the same scene before moving to the next one.

# 2. What GPU-driven rendering changes

A useful way of thinking about GPU-driven rendering is that we are changing a draw from a **collection of CPU state** into a **collection of GPU indices**.

Today a `RenderObject` effectively says:

```text
Use this MaterialInstance pointer
Use this VkBuffer
Use this vertex device address
Use this transform
Draw this index range
```

We want it to become something closer to:

```text
Object 124
    mesh = 51
    material = 8
    transform = ...
    bounds = ...
```

Then the GPU can do:

```text
object 124
    |
    +--> mesh table[51]
    |       vertex address
    |       first index
    |       index count
    |
    +--> material table[8]
            base-color texture index
            metal/rough texture index
            factors
```

The compute shader can decide if object 124 is visible and, if it is, write:

```cpp
VkDrawIndexedIndirectCommand command;
```

The graphics pipeline then consumes that command without the CPU having to record a draw specifically for object 124.

The target opaque path is:

```text
DrawContext::OpaqueSurfaces
          |
          v
GPUObjectData[]
          |
          v
Compute culling
          |
          +--> VkDrawIndexedIndirectCommand[]
          |
          +--> drawCount
          |
          v
vkCmdDrawIndexedIndirectCount()
```

For the first implementation, the `DrawContext` will still be generated every frame. Later in the chapter we will discuss turning this into a retained GPU scene so static objects do not need to be rebuilt every frame.

## Theory interlude — the CPU/GPU execution model behind GPU-driven rendering

Before implementing the checkpoints below, it is worth understanding **why GPU-driven rendering exists at all**. If the only mental model you keep is “indirect drawing is faster,” you will know a technique but not the engineering problem it solves.

### A draw call is not just a function call

When C++ executes:

```cpp
vkCmdDrawIndexed(cmd, indexCount, 1, firstIndex, 0, firstInstance);
```

nothing is rendered immediately. The CPU is recording a description of future GPU work into a command buffer. Before the GPU eventually executes that draw, the CPU side has already done work such as:

```text
game/world traversal
      |
      v
visibility / sorting
      |
      v
choose pipeline/material/mesh
      |
      v
record Vulkan commands
      |
      v
submit command buffer
      |
      v
GPU command processor
      |
      v
vertex/fragment/compute hardware
```

The important observation is that **the CPU and GPU are independent processors connected by queues and memory**. The CPU should ideally prepare work while the GPU executes previous work. If the CPU spends too much time rebuilding thousands of tiny draw decisions every frame, the GPU may become underfed even when the GPU itself has plenty of capacity.

### What actually scales poorly in a CPU-driven renderer?

Suppose the scene contains 50,000 potentially visible objects. A naive renderer might do this every frame:

```cpp
for (RenderObject& object : objects)
{
    if (!is_visible(object))
        continue;

    bind_pipeline(object.pipeline);
    bind_material(object.material);
    bind_mesh(object.mesh);
    draw(object);
}
```

The problem is not that a C++ `for` loop over 50,000 elements is inherently expensive. The cost comes from the *kind* of work in the loop:

- pointer chasing through engine objects;
- branch-heavy visibility/material decisions;
- sorting and state tracking;
- descriptor and buffer binding decisions;
- command-buffer writes;
- driver/runtime bookkeeping;
- repeatedly converting high-level scene state into low-level GPU commands.

Modern CPUs are excellent at predictable arithmetic on contiguous data. They are less happy when each iteration touches unrelated heap objects and emits a different command sequence.

### Why does the GPU make a good visibility processor?

A GPU has thousands of arithmetic lanes designed to execute the same operation over many independent elements. Visibility testing often looks like:

```text
object 0 -> test bounds
object 1 -> test bounds
object 2 -> test bounds
...
object N -> test bounds
```

That is naturally data-parallel.

Instead of the CPU producing *draw commands for visible objects*, we can upload a compact description of all candidate objects:

```text
GPUObjectData[]
    transform
    bounds
    mesh index
    material index
```

and let a compute shader perform:

```text
one invocation / object
       |
       +--> invisible -> emit nothing
       |
       +--> visible   -> append indirect command
```

The CPU is no longer responsible for the per-object draw decision.

### Why indirect drawing is the bridge

A compute shader cannot call a Vulkan API function. It cannot execute:

```cpp
vkCmdDrawIndexed(...);
```

Vulkan commands are created by the host CPU.

What the GPU *can* do is write memory. Vulkan therefore provides indirect commands where drawing parameters are read from GPU-visible memory:

```text
CPU records once:

vkCmdDrawIndexedIndirectCount(...)
              |
              v
GPU reads command buffer at execution time
```

Now compute can generate the contents of that indirect buffer before the graphics pipeline consumes it.

That is the core mechanism:

```text
scene data
   |
   v
compute shader
   |
   +--> indirect command buffer
   +--> draw count
   |
   v
indirect draw command already recorded by CPU
```

### Why do meshes and materials need to become indices?

An indirect command can contain fields such as index count, first index, vertex offset, instance count, and first instance. It cannot say:

```text
call vkCmdBindDescriptorSets(materialA)
call vkCmdBindIndexBuffer(meshB)
```

Those are host-side Vulkan commands.

So the scene representation must change from **CPU objects containing bindable state** into **GPU records containing indices**.

That is why GPU-driven rendering tends to create tables:

```text
Object table
    object -> mesh index, material index, transform

Mesh table
    mesh -> vertex address, first index, index count

Material table
    material -> texture indices, factors

Texture table
    texture index -> descriptor
```

This is not style. It follows from the fact that the GPU can efficiently follow data references but cannot dynamically issue arbitrary host API calls.

### CPU-driven, GPU-driven, and mesh-shader approaches are points on a spectrum

Do not think of GPU-driven rendering as universally superior.

```text
CPU-driven
    CPU decides visibility and records draws

Indirect/batched
    CPU decides visibility but emits fewer API commands

GPU-driven indirect
    GPU decides visibility and writes indirect work

Mesh/task shader driven
    GPU can perform even more geometry selection/amplification internally
```

For a scene with only a few hundred objects, CPU-driven rendering can be simpler and fast enough. GPU-driven architectures earn their complexity when the amount of potential render work becomes large enough that CPU submission, visibility, or state-management overhead matters.

### The engineering question to ask

Never ask only:

> Is GPU-driven rendering faster?

Ask:

> What part of my frame is currently expensive, and does moving per-object decision making to GPU-parallel data processing remove that bottleneck without creating a worse GPU bottleneck?

A GPU culling pass can itself become expensive. It consumes bandwidth, compute resources, buffers, synchronization, and debugging complexity. The architecture is justified when measured total frame cost improves or when it enables a scale of scene that the CPU-driven path cannot sustain.

### Reasoning checkpoint

Before continuing, you should be able to explain without looking at this chapter:

1. Why a GPU cannot simply call `vkCmdDrawIndexed()` from a compute shader.
2. Why indirect commands make GPU-generated work possible.
3. Why bindless resources and GPU tables naturally appear in GPU-driven designs.
4. Why Buffer Device Address lets us keep separate vertex buffers while a global index-buffer strategy solves indirect index binding.
5. Why fewer API calls alone are not the whole point—the larger goal is moving repetitive per-object decisions away from the CPU.

# 3. The implementation plan

We are going to build the renderer in these checkpoints.

## Checkpoint A — indirect drawing works

Keep the existing Chapter 5 material and mesh bindings, but replace one `vkCmdDrawIndexed()` with one `vkCmdDrawIndexedIndirect()`.

Nothing becomes faster yet.

The point is only to prove that the device features, buffer usage, command layout, and offsets are correct.

## Checkpoint B — all opaque meshes share one bound index buffer

The GPU cannot change `vkCmdBindIndexBuffer()` from inside an indirect command.

We therefore create a large global index-buffer arena.

The nice part is that we **do not need to merge the vertex buffers**. Chapter 5 already uses Buffer Device Address for vertex pulling, so every mesh can keep its own vertex buffer.

## Checkpoint C — materials become data

An indirect command also cannot call `vkCmdBindDescriptorSets()`.

We create:

- one bindless texture descriptor array;
- one `GPUMaterialData[]` table;
- a material index on every object.

We leave the existing `MaterialInstance` system alive for transparent rendering.

## Checkpoint D — one CPU-generated indirect call renders all opaque objects

The CPU fills an array of `VkDrawIndexedIndirectCommand` structures.

Then opaque rendering becomes one call:

```cpp
vkCmdDrawIndexedIndirectCount(...);
```

At this point the graphics side is ready for GPU-generated commands.

## Checkpoint E — compute shader generates the commands

The compute shader loops through objects and writes indirect commands.

Initially every object survives.

## Checkpoint F — move Chapter 5 frustum culling to compute

We reuse the same bounds that Chapter 5 already calculated.

The CPU no longer culls opaque objects.

## Checkpoint G — add occlusion culling

We create a hierarchical depth image and use it from the next frame's culling pass.

This is where the renderer becomes much closer to a production GPU-driven architecture.

# 4. Enable the Vulkan features we need

The current VKGuide initializes Vulkan 1.3 through vk-bootstrap and already enables Dynamic Rendering, Synchronization2, Buffer Device Address, and descriptor indexing.

For this chapter, we need to make the indirect-draw requirements explicit too.

Go to the device creation code in `VulkanEngine::init_vulkan()`.

You should already have something similar to:

```cpp
VkPhysicalDeviceVulkan13Features features13{};
features13.sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_3_FEATURES;
features13.dynamicRendering = true;
features13.synchronization2 = true;

VkPhysicalDeviceVulkan12Features features12{};
features12.sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_2_FEATURES;
features12.bufferDeviceAddress = true;
features12.descriptorIndexing = true;
```

Add the features we are going to use:

```cpp
features12.drawIndirectCount = true;
features12.shaderSampledImageArrayNonUniformIndexing = true;
```

We are going to use a **fixed-size** descriptor array in this tutorial, so we do not need variable descriptor count or update-after-bind yet.

We also need two regular `VkPhysicalDeviceFeatures`:

```cpp
VkPhysicalDeviceFeatures baseFeatures{};
baseFeatures.multiDrawIndirect = VK_TRUE;
baseFeatures.drawIndirectFirstInstance = VK_TRUE;
```

Then pass those to vk-bootstrap along with the Vulkan 1.2 and 1.3 feature structures.

Depending on the exact vk-bootstrap version used by your checkout, the call is typically along these lines:

```cpp
vkb::DeviceBuilder deviceBuilder{ physicalDevice };

vkb::Device vkbDevice = deviceBuilder
    .add_pNext(&features13)
    .add_pNext(&features12)
    .set_required_features(baseFeatures)
    .build()
    .value();
```

If your current VKGuide checkout uses `set_required_features_13()` / `set_required_features_12()`, keep that style and only add the new fields.

The exact builder spelling is less important than enabling these Vulkan feature bits:

```text
dynamicRendering
synchronization2
bufferDeviceAddress
descriptorIndexing
shaderSampledImageArrayNonUniformIndexing
drawIndirectCount
multiDrawIndirect
drawIndirectFirstInstance
```

## Why `drawIndirectFirstInstance` matters

Later, every generated draw will contain:

```cpp
command.firstInstance = objectID;
```

In the vertex shader we will retrieve that value through:

```glsl
uint objectID = gl_InstanceIndex;
```

If `drawIndirectFirstInstance` is not enabled, indirect commands are restricted from using non-zero `firstInstance` values.

## Why `multiDrawIndirect` matters

We want one Vulkan command to execute many `VkDrawIndexedIndirectCommand` entries.

That is exactly the use case this feature exists for.

# 5. First step: draw indirectly without changing the renderer

Before creating a GPU scene, we will prove that indirect drawing works using the exact Chapter 5 draw loop.

An indexed indirect command is this Vulkan structure:

```cpp
VkDrawIndexedIndirectCommand command{};
command.indexCount = r.indexCount;
command.instanceCount = 1;
command.firstIndex = r.firstIndex;
command.vertexOffset = 0;
command.firstInstance = 0;
```

Those fields correspond closely to:

```cpp
vkCmdDrawIndexed(
    cmd,
    r.indexCount,
    1,
    r.firstIndex,
    0,
    0);
```

The difference is that Vulkan reads the arguments from a buffer instead of from the command stream.

## Add a temporary indirect buffer

For this first test, add one mapped buffer to `FrameData`.

In the file where your frame resources are declared, add:

```cpp
struct FrameData
{
    // existing Chapter 5 members...

    AllocatedBuffer testIndirectBuffer;
};
```

When you create the per-frame resources, allocate it as:

```cpp
frame.testIndirectBuffer = create_buffer(
    sizeof(VkDrawIndexedIndirectCommand) * 4096,
    VK_BUFFER_USAGE_INDIRECT_BUFFER_BIT,
    VMA_MEMORY_USAGE_CPU_TO_GPU);
```

4096 is only a temporary capacity for this test. We will replace this buffer later.

Also destroy it with the rest of the frame resources.

## Replace one direct draw

Inside the Chapter 5 `draw()` lambda, keep all the existing state binding:

```cpp
if (r.material != lastMaterial) {
    // existing material/pipeline binding
}

if (r.indexBuffer != lastIndexBuffer) {
    vkCmdBindIndexBuffer(cmd, r.indexBuffer, 0, VK_INDEX_TYPE_UINT32);
}

GPUDrawPushConstants pushConstants;
pushConstants.worldMatrix = r.transform;
pushConstants.vertexBuffer = r.vertexBufferAddress;

vkCmdPushConstants(
    cmd,
    r.material->pipeline->layout,
    VK_SHADER_STAGE_VERTEX_BIT,
    0,
    sizeof(GPUDrawPushConstants),
    &pushConstants);
```

Instead of calling `vkCmdDrawIndexed()`, write one indirect command into the mapped buffer:

```cpp
VkDrawIndexedIndirectCommand indirect{};
indirect.indexCount = r.indexCount;
indirect.instanceCount = 1;
indirect.firstIndex = r.firstIndex;
indirect.vertexOffset = 0;
indirect.firstInstance = 0;

memcpy(
    get_current_frame().testIndirectBuffer.info.pMappedData,
    &indirect,
    sizeof(indirect));
```

If your mapped memory type is not host coherent, flush it:

```cpp
vmaFlushAllocation(
    _allocator,
    get_current_frame().testIndirectBuffer.allocation,
    0,
    sizeof(indirect));
```

Then draw with:

```cpp
vkCmdDrawIndexedIndirect(
    cmd,
    get_current_frame().testIndirectBuffer.buffer,
    0,
    1,
    sizeof(VkDrawIndexedIndirectCommand));
```

The scene should look exactly the same.

## What did we accomplish?

Almost nothing performance-wise.

We still:

- bind every material;
- bind every index buffer;
- push every transform;
- record one Vulkan draw command for every object.

But we have verified the first important piece: the GPU can read a `VkDrawIndexedIndirectCommand` from memory and execute it correctly.

This is a good debugging checkpoint.

Once it works, revert the Chapter 5 loop back to `vkCmdDrawIndexed()` for now. We are going to introduce the real indirect path separately instead of leaving this temporary test inside the old renderer.

# 7. Building one index-buffer arena

This is the first architectural problem we need to solve.

## Why one index buffer?

An indirect command can specify:

```cpp
indexCount
instanceCount
firstIndex
vertexOffset
firstInstance
```

It cannot specify a `VkBuffer`.

The index buffer still comes from:

```cpp
vkCmdBindIndexBuffer();
```

That means all commands executed by one large multi-draw must be able to use the same bound index buffer.

Chapter 5 uploads one index buffer per mesh, so we need to change that for the GPU-driven path.

## We do not need to merge vertex buffers

This is where your Chapter 5 renderer gives us an advantage.

Vertices are already fetched manually using Buffer Device Address:

```glsl
Vertex v = PushConstants.vertexBuffer.vertices[gl_VertexIndex];
```

So each draw can still use a different vertex-buffer address stored in GPU data.

We only need one global buffer for **indices**.

The layout will be:

```text
Global Index Buffer

| surface A indices | surface B indices | surface C indices | ...
^                   ^
0                   firstIndexB
```

Each GPU mesh record stores the `firstIndex` where its indices were copied.

## Make existing index buffers copyable

We want to register existing Chapter 5 meshes into the new arena during GLTF loading.

Go to `VulkanEngine::uploadMesh()`.

The current index-buffer usage is approximately:

```cpp
VK_BUFFER_USAGE_INDEX_BUFFER_BIT |
VK_BUFFER_USAGE_TRANSFER_DST_BIT
```

Add `TRANSFER_SRC`:

```cpp
newSurface.indexBuffer = create_buffer(
    indexBufferSize,
    VK_BUFFER_USAGE_INDEX_BUFFER_BIT |
    VK_BUFFER_USAGE_TRANSFER_DST_BIT |
    VK_BUFFER_USAGE_TRANSFER_SRC_BIT,
    VMA_MEMORY_USAGE_GPU_ONLY);
```

The existing renderer behaves exactly the same. We only added permission to copy from the buffer later.

## Allocate the arena

In `init_gpu_driven()` allocate a reasonably large buffer.

For the tutorial, 128 MiB is fine:

```cpp
constexpr VkDeviceSize globalIndexBufferSize = 128ull * 1024ull * 1024ull;

gpuDriven.globalIndexBuffer = create_buffer(
    globalIndexBufferSize,
    VK_BUFFER_USAGE_INDEX_BUFFER_BIT |
    VK_BUFFER_USAGE_TRANSFER_DST_BIT,
    VMA_MEMORY_USAGE_GPU_ONLY);
```

A 32-bit index uses 4 bytes, so 128 MiB can contain roughly 33 million indices.

This is a simple linear arena. It does not support freeing individual ranges yet.

That is fine for this tutorial because our Chapter 5 scenes are loaded as large GLTF assets and generally live for a long time.

## What about production code?

Eventually you would probably use one of:

- a free-list allocator;
- a buddy allocator;
- large geometry pages;
- per-level arenas;
- defragmentation/relocation;
- mesh streaming pages.

Do not build that yet.

We are trying to understand GPU-driven rendering, not write a general-purpose VRAM allocator.

# 8. Giving meshes stable GPU indices

We now need a small record that the GPU can use to find mesh geometry.

Add this to `vk_types.h` or `vk_gpu_driven.h`:

```cpp
struct GPUMeshData
{
    VkDeviceAddress vertexBufferAddress;
    uint32_t firstIndex;
    uint32_t indexCount;
};

static_assert(sizeof(GPUMeshData) == 16);
```

Notice what is missing:

```text
VkBuffer indexBuffer
```

Every opaque draw uses `gpuDriven.globalIndexBuffer`, so there is no need to store an index-buffer handle per mesh.

## Allocate the mesh table

## Register a surface

Add this function:

```cpp
uint32_t VulkanEngine::register_gpu_mesh(
    VkBuffer sourceIndexBuffer,
    VkDeviceAddress vertexBufferAddress,
    uint32_t sourceFirstIndex,
    uint32_t indexCount)
{
    assert(gpuDriven.meshCount < GPUDrivenRenderer::MaxMeshes);

    const uint32_t meshIndex = gpuDriven.meshCount++;
    const uint32_t destinationFirstIndex = gpuDriven.nextGlobalIndex;

    const VkDeviceSize copySize =
        VkDeviceSize(indexCount) * sizeof(uint32_t);

    const VkDeviceSize sourceOffset =
        VkDeviceSize(sourceFirstIndex) * sizeof(uint32_t);

    const VkDeviceSize destinationOffset =
        VkDeviceSize(destinationFirstIndex) * sizeof(uint32_t);

    immediate_submit([&](VkCommandBuffer cmd) {
        VkBufferCopy copy{};
        copy.srcOffset = sourceOffset;
        copy.dstOffset = destinationOffset;
        copy.size = copySize;

        vkCmdCopyBuffer(
            cmd,
            sourceIndexBuffer,
            gpuDriven.globalIndexBuffer.buffer,
            1,
            &copy);
    });

    gpuDriven.nextGlobalIndex += indexCount;

    auto* meshes = reinterpret_cast<GPUMeshData*>(
        gpuDriven.meshBuffer.info.pMappedData);

    meshes[meshIndex].vertexBufferAddress = vertexBufferAddress;
    meshes[meshIndex].firstIndex = destinationFirstIndex;
    meshes[meshIndex].indexCount = indexCount;

    vmaFlushAllocation(
        _allocator,
        gpuDriven.meshBuffer.allocation,
        sizeof(GPUMeshData) * meshIndex,
        sizeof(GPUMeshData));

    return meshIndex;
}
```

For simplicity, add a capacity check for the global index arena too. Keep its capacity as a member rather than hardcoding it inside the registration function.

# 9. Creating a bindless texture table

The index-buffer problem is solved, but we still cannot multi-draw arbitrary materials.

Chapter 5 binds a material descriptor set whenever the material changes:

```cpp
vkCmdBindDescriptorSets(
    cmd,
    VK_PIPELINE_BIND_POINT_GRAPHICS,
    r.material->pipeline->layout,
    1,
    1,
    &r.material->materialSet,
    0,
    nullptr);
```

An indirect command cannot perform that bind.

We need textures to be selected using data.

The simplest modern solution is a descriptor array:

```glsl
layout(set = 1, binding = 0)
uniform sampler2D textures[4096];
```

A material then stores integer texture indices:

```text
material 17
    baseColorTexture = 42
    metalRoughTexture = 91
```

## Keep this first bindless implementation simple

There are many advanced descriptor-indexing features:

- variable descriptor counts;
- runtime arrays;
- partially bound descriptors;
- update-after-bind;
- descriptor buffers;
- descriptor heaps.

We do not need them yet.

For the first version we will use a fixed array and initialize **every slot** to a valid default texture.

That lets us avoid partially-bound and update-after-bind complexity while still learning the architecture.

## Extend `DescriptorLayoutBuilder`

Chapter 4's helper creates one descriptor per binding.

Change `add_binding()` so it accepts a count:

```cpp
void DescriptorLayoutBuilder::add_binding(
    uint32_t binding,
    VkDescriptorType type,
    uint32_t count)
{
    VkDescriptorSetLayoutBinding newBinding{};
    newBinding.binding = binding;
    newBinding.descriptorCount = count;
    newBinding.descriptorType = type;

    bindings.push_back(newBinding);
}
```

Give `count` a default of 1 in the declaration so all old calls remain valid:

```cpp
void add_binding(
    uint32_t binding,
    VkDescriptorType type,
    uint32_t count = 1);
```

## Create the bindless layout

In `init_gpu_driven()`:

```cpp
DescriptorLayoutBuilder builder;
builder.add_binding(
    0,
    VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER,
    GPUDrivenRenderer::MaxTextures);

gpuDriven.bindlessTextureLayout = builder.build(
    _device,
    VK_SHADER_STAGE_FRAGMENT_BIT);
```

Before committing to 4096, query the device limits in your renderer and make sure both the relevant per-stage and descriptor-set sampled-image limits are high enough.

For the PC GPUs targeted by this tutorial, requiring a few thousand descriptors is reasonable. If your device exposes a lower limit, lower `MaxTextures` and change the shader array size to match.

## Create a dedicated descriptor pool

We only need one very large descriptor set:

```cpp
std::vector<DescriptorAllocatorGrowable::PoolSizeRatio> sizes = {
    { VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER,
      float(GPUDrivenRenderer::MaxTextures) }
};

gpuDriven.bindlessAllocator.init(_device, 1, sizes);

gpuDriven.bindlessTextureSet =
    gpuDriven.bindlessAllocator.allocate(
        _device,
        gpuDriven.bindlessTextureLayout);
```

If your allocator's ratio semantics differ, allocate enough combined-image-sampler descriptors for `MaxTextures`. The goal is one set containing the entire array.

## Fill the whole table with a default

Create an array of descriptor image info:

```cpp
std::vector<VkDescriptorImageInfo> defaults(
    GPUDrivenRenderer::MaxTextures);

for (VkDescriptorImageInfo& info : defaults)
{
    info.sampler = _defaultSamplerLinear;
    info.imageView = _whiteImage.imageView;
    info.imageLayout = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL;
}
```

Write the full array:

```cpp
VkWriteDescriptorSet write{};
write.sType = VK_STRUCTURE_TYPE_WRITE_DESCRIPTOR_SET;
write.dstSet = gpuDriven.bindlessTextureSet;
write.dstBinding = 0;
write.dstArrayElement = 0;
write.descriptorCount = GPUDrivenRenderer::MaxTextures;
write.descriptorType = VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER;
write.pImageInfo = defaults.data();

vkUpdateDescriptorSets(
    _device,
    1,
    &write,
    0,
    nullptr);
```

Reserve index 0 as the default white texture:

```cpp
gpuDriven.textureCount = 1;
```

## Register one texture/sampler pair

Add:

```cpp
uint32_t VulkanEngine::register_gpu_texture(
    VkImageView imageView,
    VkSampler sampler)
{
    assert(gpuDriven.textureCount < GPUDrivenRenderer::MaxTextures);

    uint32_t index = gpuDriven.textureCount++;

    VkDescriptorImageInfo imageInfo{};
    imageInfo.sampler = sampler;
    imageInfo.imageView = imageView;
    imageInfo.imageLayout = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL;

    VkWriteDescriptorSet write{};
    write.sType = VK_STRUCTURE_TYPE_WRITE_DESCRIPTOR_SET;
    write.dstSet = gpuDriven.bindlessTextureSet;
    write.dstBinding = 0;
    write.dstArrayElement = index;
    write.descriptorCount = 1;
    write.descriptorType = VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER;
    write.pImageInfo = &imageInfo;

    vkUpdateDescriptorSets(_device, 1, &write, 0, nullptr);

    return index;
}
```

### Important lifetime rule

This first version updates the descriptor table while assets are loading, before those descriptors are being used by in-flight command buffers.

Do **not** start streaming textures and overwriting descriptors while old frames are using the set unless you add the proper update-after-bind design and lifetime management.

We will keep asset loading simple, just like the earlier VKGuide chapters.

# 12. Creating the per-frame GPU object buffer

Meshes and materials are mostly asset data, so we made them persistent.

Objects are different.

Their transforms can change every frame, and Chapter 5 already rebuilds the `DrawContext` each frame.

For the first GPU-driven implementation we will preserve that architecture:

```text
scene graph
    |
    v
DrawContext::OpaqueSurfaces
    |
    v
copy into this frame's GPUObjectData[]
```

Later we will turn this into retained scene data.

## GPU object structure

We want enough data to reproduce Chapter 5's culling exactly.

Add:

```cpp
struct alignas(16) GPUObjectData
{
    glm::mat4 transform;

    // xyz = local-space bounds center
    // w   = sphere radius
    glm::vec4 boundsOriginRadius;

    // xyz = local-space box extents
    glm::vec4 boundsExtents;

    uint32_t meshIndex;
    uint32_t materialIndex;
    uint32_t flags;
    uint32_t padding;
};

static_assert(sizeof(GPUObjectData) == 112);
```

We store both sphere and box bounds because they are useful for different culling algorithms.

For the first culling shader, we will use the box extents so it behaves similarly to Chapter 5's CPU implementation.

## Per-frame buffers

Add these to `FrameData`:

```cpp
struct FrameData
{
    // existing resources...

    AllocatedBuffer gpuObjectBuffer;
    VkDeviceAddress gpuObjectBufferAddress = 0;

    AllocatedBuffer gpuIndirectBuffer;
    VkDeviceAddress gpuIndirectBufferAddress = 0;

    AllocatedBuffer gpuDrawCountBuffer;
    VkDeviceAddress gpuDrawCountBufferAddress = 0;
};
```

### Object buffer

The CPU updates this every frame, so start with CPU-visible memory:

### Indirect buffer


### Draw-count buffer

```cpp

    VK_BUFFER_USAGE_STORAGE_BUFFER_BIT |
    VK_BUFFER_USAGE_INDIRECT_BUFFER_BIT |
```

```cpp
VkDeviceAddress VulkanEngine::get_buffer_address(VkBuffer buffer)
{
    VkBufferDeviceAddressInfo info{};

    info.buffer = buffer;

```

Then:

```cpp

    get_buffer_address(frame.gpuIndirectBuffer.buffer);

    get_buffer_address(frame.gpuDrawCountBuffer.buffer);
```

Do this for every frame in flight.

## Upload the current DrawContext

Add:

```cpp
uint32_t VulkanEngine::upload_gpu_objects()
{
    FrameData& frame = get_current_frame();

    const uint32_t objectCount = static_cast<uint32_t>(
        mainDrawContext.OpaqueSurfaces.size());

    assert(objectCount <= GPUDrivenRenderer::MaxObjects);

    auto* gpuObjects = reinterpret_cast<GPUObjectData*>(
        frame.gpuObjectBuffer.info.pMappedData);

    for (uint32_t i = 0; i < objectCount; ++i)
    {
        const RenderObject& object =
            mainDrawContext.OpaqueSurfaces[i];

        GPUObjectData& gpu = gpuObjects[i];

        gpu.transform = object.transform;
        gpu.boundsOriginRadius = glm::vec4(
            object.bounds.origin,
            object.bounds.sphereRadius);
        gpu.boundsExtents = glm::vec4(
            object.bounds.extents,
            0.0f);

        gpu.meshIndex = object.gpuMeshIndex;
        gpu.materialIndex = object.gpuMaterialIndex;
        gpu.flags = 0;
        gpu.padding = 0;
    }

    if (objectCount > 0)
    {
        vmaFlushAllocation(
            _allocator,
            frame.gpuObjectBuffer.allocation,
            0,
            sizeof(GPUObjectData) * objectCount);
    }

    return objectCount;
}
```

For now, this is still CPU work proportional to object count.

That is okay.

The first major win is moving **visibility and draw-command generation** off the CPU. Retaining and incrementally updating the object table comes later.

## Vertex shader

Create `gpu_mesh.vert`:

```glsl
#version 460

#extension GL_GOOGLE_include_directive : require
#extension GL_EXT_buffer_reference : require

#include "gpu_scene.glsl"

layout(location = 0) out vec3 outNormal;
layout(location = 1) out vec3 outColor;
layout(location = 2) out vec2 outUV;
layout(location = 3) flat out uint outMaterialIndex;

void main()
{
    // firstInstance in the indirect command becomes gl_InstanceIndex.
    uint objectID = gl_InstanceIndex;

    GPUObjectData object = gpuScene.objects.objects[objectID];
    GPUMeshData mesh = gpuScene.meshes.meshes[object.meshIndex];

    // gl_VertexIndex comes from the currently bound global index buffer.
    // The index values are still local to this mesh's vertex buffer.
    Vertex v = mesh.vertexBuffer.vertices[gl_VertexIndex];

    vec4 worldPosition =
        object.transform * vec4(v.position, 1.0);

    gl_Position = sceneData.viewproj * worldPosition;

    outNormal =
        (object.transform * vec4(v.normal, 0.0)).xyz;

    outColor = v.color.xyz;
    outUV = vec2(v.uv_x, v.uv_y);
    outMaterialIndex = object.materialIndex;
}
```

There is an important detail here.

The GPU mesh stores `firstIndex`, but the vertex shader does not use it. The fixed-function indexed draw hardware uses `firstIndex` when reading the global index buffer.

The actual value retrieved from the index buffer then becomes `gl_VertexIndex`.

Because we copied each surface's original indices unchanged, that value still correctly indexes the mesh-specific vertex buffer.

This is why we can keep separate BDA vertex buffers while using one global fixed-function index buffer.

## Fragment shader

Create `gpu_mesh.frag`:

```glsl
#version 460

#extension GL_GOOGLE_include_directive : require
#extension GL_EXT_buffer_reference : require
#extension GL_EXT_nonuniform_qualifier : require

#include "gpu_scene.glsl"

layout(set = 1, binding = 0)
uniform sampler2D textures[4096];

layout(location = 0) in vec3 inNormal;
layout(location = 1) in vec3 inColor;
layout(location = 2) in vec2 inUV;
layout(location = 3) flat in uint inMaterialIndex;

layout(location = 0) out vec4 outFragColor;

void main()
{
    GPUMaterialData material =
        gpuScene.materials.materials[inMaterialIndex];

    vec3 normal = normalize(inNormal);

    float lightValue = max(
        dot(normal, sceneData.sunlightDirection.xyz),
        0.1);

    vec3 baseColor = texture(
        textures[nonuniformEXT(material.colorTexture)],
        inUV).rgb;

    vec3 color =
        inColor * material.colorFactors.rgb * baseColor;

    vec3 ambient =
        color * sceneData.ambientColor.xyz;

    outFragColor = vec4(
        color * lightValue * sceneData.sunlightColor.w + ambient,
        1.0);
}
```

We are intentionally keeping the lighting close to Chapter 5.

This chapter is about draw architecture, not physically based lighting.



If you change one, change the other.

Later you can use runtime descriptor arrays and variable descriptor counts, but a fixed compile-time size is easier to debug first.

## Create the pipeline layout

The pipeline needs two descriptor sets:

```text

```

And the three table addresses through push constants.

```cpp
VkDescriptorSetLayout layouts[] = {
    _gpuSceneDataDescriptorLayout,
    gpuDriven.bindlessTextureLayout
};

VkPushConstantRange pushRange{};
pushRange.offset = 0;
pushRange.size = sizeof(GPUDrivenDrawPushConstants);
pushRange.stageFlags =
    VK_SHADER_STAGE_VERTEX_BIT |
    VK_SHADER_STAGE_FRAGMENT_BIT;

VkPipelineLayoutCreateInfo layoutInfo =
    vkinit::pipeline_layout_create_info();

layoutInfo.setLayoutCount = 2;
layoutInfo.pSetLayouts = layouts;
```

## Build the commands

After `upload_gpu_objects()`, create one command per opaque object:

```cpp
void VulkanEngine::build_indirect_commands_cpu(uint32_t objectCount)
{
    FrameData& frame = get_current_frame();

    auto* commands =
        reinterpret_cast<VkDrawIndexedIndirectCommand*>(
            frame.gpuIndirectBuffer.info.pMappedData);

    for (uint32_t objectID = 0;
         objectID < objectCount;
         ++objectID)
    {
        const RenderObject& object =
            mainDrawContext.OpaqueSurfaces[objectID];

        const auto* meshes =
            reinterpret_cast<const GPUMeshData*>(
                gpuDriven.meshBuffer.info.pMappedData);

        const GPUMeshData& mesh =
            meshes[object.gpuMeshIndex];

        VkDrawIndexedIndirectCommand& command =
            commands[objectID];

        command.indexCount = mesh.indexCount;
        command.instanceCount = 1;
        command.firstIndex = mesh.firstIndex;
        command.vertexOffset = 0;

        // This is how the vertex shader discovers the object.
        command.firstInstance = objectID;
    }

    *reinterpret_cast<uint32_t*>(
        frame.gpuDrawCountBuffer.info.pMappedData) = objectCount;

    if (objectCount > 0)
    {
        vmaFlushAllocation(
            _allocator,
            frame.gpuIndirectBuffer.allocation,
            0,
            sizeof(VkDrawIndexedIndirectCommand) * objectCount);
    }

    vmaFlushAllocation(
        _allocator,
        frame.gpuDrawCountBuffer.allocation,
        0,
        sizeof(uint32_t));
}
```

Reading `meshBuffer.info.pMappedData` is fine here because we deliberately allocated the first version of the persistent mesh table as CPU-visible memory.

# 16. Moving draw generation to a compute shader

At the previous checkpoint the CPU wrote every indirect command.

Now we are ready for the actual GPU-driven part.


## Matching the Vulkan indirect-command layout in GLSL

Create `shaders/gpu_cull.comp`.

```glsl
#version 460

#extension GL_GOOGLE_include_directive : require
#extension GL_EXT_buffer_reference : require

#include "gpu_scene.glsl"

{
    uint indexCount;
    uint instanceCount;

    uint firstInstance;
};

    DrawIndexedIndirectCommand commands[];
};

    uint count;
};
```

The field order is important. It must match Vulkan's `VkDrawIndexedIndirectCommand` exactly.

## Compute push constants

On C++ add:

```cpp
struct GPUCullPushConstants
{
    VkDeviceAddress objectBuffer;
    VkDeviceAddress meshBuffer;
    VkDeviceAddress commandBuffer;
    VkDeviceAddress drawCountBuffer;

    uint32_t objectCount;
    uint32_t padding;
};

static_assert(sizeof(GPUCullPushConstants) == 40);
```

The matching shader block is:

```glsl
layout(push_constant) uniform CullPushConstants
{
    ObjectBuffer objects;
    MeshBuffer meshes;
    DrawCommandBuffer commands;
    DrawCountBuffer drawCount;

    uint objectCount;
    uint padding;
} cull;
```

## First compute shader: no culling

Use 64 threads per workgroup:

```glsl
layout(local_size_x = 64) in;

void main()
{
    uint objectID = gl_GlobalInvocationID.x;

    if (objectID >= cull.objectCount)
        return;

    GPUObjectData object = cull.objects.objects[objectID];
    GPUMeshData mesh = cull.meshes.meshes[object.meshIndex];

    uint drawID = atomicAdd(cull.drawCount.count, 1);

    DrawIndexedIndirectCommand command;
    command.indexCount = mesh.indexCount;
    command.instanceCount = 1;
    command.firstIndex = mesh.firstIndex;
    command.vertexOffset = 0;
    command.firstInstance = objectID;

    cull.commands.commands[drawID] = command;
}
```

The `atomicAdd()` performs two jobs:

1. it gives this visible object a unique output slot;
2. it increments the final draw count.

Right now all objects are visible, so the final count will equal `objectCount`.

Once we add culling, invisible objects simply return before the atomic operation.

That automatically compacts the output array.

This is a much cleaner model than leaving zero-sized indirect commands in a large fixed array.

## Theory interlude — Vulkan synchronization from first principles

The next code contains barriers. Do **not** learn the barriers as recipes. The goal of this interlude is to make you capable of deriving a barrier for a dependency you have never seen before.

### Three facts must be kept separate

A common source of confusion is treating these as the same thing:

```text
1. API / command order
2. execution order
3. memory visibility
```

They are related, but they are not identical.

If a command buffer contains:

```text
A
B
C
```

that tells Vulkan the order in which commands were recorded. It does **not** mean all hardware work from A finishes before any hardware work from B begins.

A GPU is deeply pipelined. Conceptually:

```text
Draw A:  vertex -------- fragment --------
Draw B:          vertex -------- fragment --------
Draw C:                 vertex -------- fragment --------
```

Different commands and different pipeline stages can overlap.

That overlap is essential for performance. Synchronization exists so we restrict overlap **only where correctness requires it**.

### A dependency begins with a resource hazard

Ignore Vulkan enums for a moment. Start with one resource `X`.

#### RAW — Read After Write

```text
Pass A: write X
Pass B: read X
```

B needs the value produced by A.

This is the most common rendering dependency.

Example:

```text
compute culling writes indirect commands
indirect draw reads indirect commands
```

#### WAR — Write After Read

```text
Pass A: read X
Pass B: write X
```

B must not overwrite X while A is still consuming the old contents.

#### WAW — Write After Write

```text
Pass A: write X
Pass B: write X
```

If the order of the two results matters, the writes must be ordered.

There is normally no hazard for:

```text
read -> read
```

because neither operation modifies the resource.

### Execution dependency: *when* may the consumer proceed?

Pipeline stage masks describe execution scopes.

For a dependency:

```text
producer ----> consumer
```

ask:

> In which stage does the producer perform the relevant operation?

and:

> In which stage does the consumer perform the dependent operation?

For our indirect example:

```text
compute shader writes command memory
              |
              v
DRAW_INDIRECT stage reads command memory
```

So the execution relationship is roughly:

```cpp
srcStageMask = VK_PIPELINE_STAGE_2_COMPUTE_SHADER_BIT;
dstStageMask = VK_PIPELINE_STAGE_2_DRAW_INDIRECT_BIT;
```

Do not mechanically choose `ALL_COMMANDS`. A wider scope can be correct, but it throws away information and may unnecessarily restrict overlap.

### Memory dependency: *which* accesses must become visible?

Stage masks alone do not describe the memory operations.

Access masks answer:

> What kind of producer memory operation must be made available?

and:

> What kind of consumer access must observe it?

For the same example:

```cpp
srcAccessMask = VK_ACCESS_2_SHADER_WRITE_BIT;
dstAccessMask = VK_ACCESS_2_INDIRECT_COMMAND_READ_BIT;
```

A useful mental model is:

```text
src stage/access
    identifies the writes we care about
           |
           v
       barrier
           |
           v
dst stage/access
    identifies the dependent accesses
```

### Availability and visibility

The Vulkan specification uses precise concepts such as *availability* and *visibility*.

A useful simplified model is:

```text
producer writes data
      |
      |  make previous writes available
      v
synchronization
      |
      |  make data visible to consumer domain/access
      v
consumer reads data
```

On coherent-looking desktop hardware, missing synchronization can appear to work for a long time. That does not make the program correct. The GPU, driver, cache hierarchy, queue scheduling, or different vendor may expose the race later.

### Deriving the Chapter 6 count-reset barrier

We do:

```cpp
vkCmdFillBuffer(drawCountBuffer, 0);
```

then compute uses the same buffer.

Reason from the operations:

```text
Producer:
    operation: vkCmdFillBuffer
    stage: TRANSFER
    access: TRANSFER_WRITE

Consumer:
    operation: compute shader atomic/read/write
    stage: COMPUTE_SHADER
    access: SHADER_READ / SHADER_WRITE
```

Therefore:

```text
TRANSFER / TRANSFER_WRITE
        ->
COMPUTE_SHADER / SHADER_READ|SHADER_WRITE
```

The barrier is not magic. It is a direct encoding of that producer/consumer relationship.

### Deriving compute -> indirect draw

Now compute writes:

```text
indirect command buffer
draw-count buffer
```

The indirect draw consumes both.

```text
Producer:
    COMPUTE_SHADER
    SHADER_WRITE

Consumer:
    DRAW_INDIRECT
    INDIRECT_COMMAND_READ
```

So:

```text
COMPUTE_SHADER / SHADER_WRITE
        ->
DRAW_INDIRECT / INDIRECT_COMMAND_READ
```

Again, derived rather than memorized.

### Images add another dimension: layout

Buffers do not have image layouts. Images do.

Suppose a pass renders to an image and the next pass samples it:

```text
Pass A
COLOR_ATTACHMENT_OUTPUT
COLOR_ATTACHMENT_WRITE
layout = COLOR_ATTACHMENT_OPTIMAL

Pass B
FRAGMENT_SHADER
SHADER_SAMPLED_READ
layout = SHADER_READ_ONLY_OPTIMAL
```

Now the synchronization problem contains both:

1. a write -> read memory dependency;
2. an image layout transition.

The image barrier expresses both.

The layout is not a decorative enum. It tells the implementation how the image will be used and may correspond to internal compression/tiling/cache expectations.

### Pipeline barriers versus semaphores

A useful first rule:

```text
inside one queue submission / command stream
    -> pipeline barriers are common

between queue submissions
    -> semaphores establish submission-level dependencies
```

A semaphore tells one submission that it cannot proceed past the relevant point until another submission signals it. You may still need correct memory scopes/layout transitions associated with that dependency.

Fences are different again: they are primarily a **GPU -> CPU completion mechanism**. A fence is what the host can wait on to learn that submitted GPU work completed.

```text
barrier   : GPU work <-> GPU work inside command execution
semaphore : submission/queue <-> submission/queue
fence     : GPU completion -> CPU observation
```

This is simplified, but it is a much better mental model than treating all three as interchangeable synchronization objects.

### Queue-family ownership is not ordinary synchronization

If a resource moves between queue families that do not share ownership implicitly, you may also need an ownership transfer.

That answers a separate question:

> Which queue family is allowed to access this resource?

Do not confuse queue ownership with visibility. A transfer can involve both ownership and memory/execution synchronization.

### Why synchronization bugs are hard

A missing dependency can produce:

- correct frames most of the time;
- corruption only on one vendor;
- corruption only under heavy GPU load;
- stale indirect counts;
- one-frame-late data;
- intermittent device loss;
- a bug that disappears when RenderDoc is attached.

This is why a rendering engineer must be able to reconstruct the resource history rather than guessing barriers until validation becomes quiet.

### The synchronization worksheet

For every dependency, write this before touching Vulkan enums:

```text
Resource:

Producer operation:
Producer stage:
Producer access:

Consumer operation:
Consumer stage:
Consumer access:

Hazard: RAW / WAR / WAW / none

Image layout before/after, if applicable:
Queue ownership change, if applicable:
Submission/queue boundary, if applicable:
```

Only then translate it into `Vk*Barrier2`, semaphore waits/signals, or both.

### Reasoning exercises

Derive the synchronization for these without copying an example:

1. Compute shader writes a storage image; fragment shader samples it.
2. Depth pass writes depth; compute pass samples the depth pyramid source.
3. Transfer queue uploads a vertex buffer; graphics queue reads it as vertex data.
4. Compute skinning writes a vertex buffer; shadow and opaque passes both read it.
5. A color attachment is reused as a color attachment next frame with no intermediate read.

For each one, identify producer, consumer, hazard, stages, accesses, layout if relevant, and whether a queue/submission boundary exists.

# 18. Synchronization2: reset → compute → indirect draw

This is the section where Vulkan synchronization becomes central.

The command order is:

```text
vkCmdFillBuffer(drawCount = 0)
        |
        v
compute shader
    reads objects/meshes
    writes commands/count
        |
        v
vkCmdDrawIndexedIndirectCount
    reads commands/count
```

The commands are in the correct order in one command buffer, but execution order alone is not enough. We also need the correct **memory dependencies**.

We will use Synchronization2, which your Vulkan 1.3 engine already uses.

## Step 1 — reset the count

Before dispatching compute:

```cpp
vkCmdFillBuffer(
    cmd,
    frame.gpuDrawCountBuffer.buffer,
    0,
    sizeof(uint32_t),
    0);
```

`vkCmdFillBuffer()` is a transfer operation.

The compute shader will then read/write that memory, so add a buffer barrier:

```cpp
VkBufferMemoryBarrier2 countResetBarrier{};
countResetBarrier.sType =
    VK_STRUCTURE_TYPE_BUFFER_MEMORY_BARRIER_2;

countResetBarrier.srcStageMask =
    VK_PIPELINE_STAGE_2_TRANSFER_BIT;
countResetBarrier.srcAccessMask =
    VK_ACCESS_2_TRANSFER_WRITE_BIT;

countResetBarrier.dstStageMask =
    VK_PIPELINE_STAGE_2_COMPUTE_SHADER_BIT;
countResetBarrier.dstAccessMask =
    VK_ACCESS_2_SHADER_READ_BIT |
    VK_ACCESS_2_SHADER_WRITE_BIT;

countResetBarrier.buffer =
    frame.gpuDrawCountBuffer.buffer;
countResetBarrier.offset = 0;
countResetBarrier.size = sizeof(uint32_t);

VkDependencyInfo resetDependency{};
resetDependency.sType =
    VK_STRUCTURE_TYPE_DEPENDENCY_INFO;
resetDependency.bufferMemoryBarrierCount = 1;
resetDependency.pBufferMemoryBarriers = &countResetBarrier;

vkCmdPipelineBarrier2(cmd, &resetDependency);
```

## Step 2 — dispatch compute

Bind the pipeline:

```cpp
vkCmdBindPipeline(
    cmd,
    VK_PIPELINE_BIND_POINT_COMPUTE,
    gpuDriven.cullPipeline);
```

Bind the same per-frame scene descriptor that graphics uses:

```cpp
vkCmdBindDescriptorSets(
    cmd,
    VK_PIPELINE_BIND_POINT_COMPUTE,
    gpuDriven.cullPipelineLayout,
    0,
    1,
    &globalDescriptor,
    0,
    nullptr);
```

Push the addresses:

```cpp
GPUCullPushConstants cullPush{};
cullPush.objectBuffer = frame.gpuObjectBufferAddress;
cullPush.meshBuffer = gpuDriven.meshBufferAddress;
cullPush.commandBuffer = frame.gpuIndirectBufferAddress;
cullPush.drawCountBuffer = frame.gpuDrawCountBufferAddress;
cullPush.objectCount = objectCount;

vkCmdPushConstants(
    cmd,
    gpuDriven.cullPipelineLayout,
    VK_SHADER_STAGE_COMPUTE_BIT,
    0,
    sizeof(cullPush),
    &cullPush);
```

Dispatch:

```cpp
const uint32_t groupCount =
    (objectCount + 63) / 64;

if (groupCount > 0)
{
    vkCmdDispatch(cmd, groupCount, 1, 1);
}
```

## Step 3 — compute writes become indirect reads

The compute shader writes:

- `gpuIndirectBuffer`;
- `gpuDrawCountBuffer`.

The next stage that consumes those writes is the draw-indirect stage.

Add two barriers:

```cpp
VkBufferMemoryBarrier2 indirectBarriers[2]{};

for (VkBufferMemoryBarrier2& barrier : indirectBarriers)
{
    barrier.sType =
        VK_STRUCTURE_TYPE_BUFFER_MEMORY_BARRIER_2;

    barrier.srcStageMask =
        VK_PIPELINE_STAGE_2_COMPUTE_SHADER_BIT;
    barrier.srcAccessMask =
        VK_ACCESS_2_SHADER_WRITE_BIT;

    barrier.dstStageMask =
        VK_PIPELINE_STAGE_2_DRAW_INDIRECT_BIT;
    barrier.dstAccessMask =
        VK_ACCESS_2_INDIRECT_COMMAND_READ_BIT;

    barrier.offset = 0;
    barrier.size = VK_WHOLE_SIZE;
}

indirectBarriers[0].buffer =
    frame.gpuIndirectBuffer.buffer;

indirectBarriers[1].buffer =
    frame.gpuDrawCountBuffer.buffer;

VkDependencyInfo indirectDependency{};
indirectDependency.sType =
    VK_STRUCTURE_TYPE_DEPENDENCY_INFO;
indirectDependency.bufferMemoryBarrierCount = 2;
indirectDependency.pBufferMemoryBarriers = indirectBarriers;

vkCmdPipelineBarrier2(cmd, &indirectDependency);
```

Now `vkCmdDrawIndexedIndirectCount()` is allowed to consume the compute output.

## Do we need a barrier for the object buffer?

The object buffer is written by the CPU before queue submission.

If you use non-coherent mapped memory, flush the written range with VMA before submission. We are not writing the object buffer from another GPU stage in this first version, so there is no compute-to-compute dependency required for it.

If you later upload object data through transfer commands, then you will need a transfer-write → compute-read dependency too.

## Theory interlude — frustum and occlusion culling as conservative visibility tests

Before moving the Chapter 5 culling code to compute, remember what culling is allowed to do.

A culling algorithm is normally **conservative**:

```text
certainly invisible -> reject
possibly visible    -> keep
```

A false positive costs performance because an invisible object is drawn. A false negative is usually a correctness bug because a visible object disappears.

### Why bounds are used instead of triangles

Testing every triangle against the frustum would defeat the purpose of culling. We use a cheap enclosing volume:

```text
sphere
AABB
OBB
meshlet bound
```

The bound contains the real geometry, so rejecting the bound guarantees that the geometry is outside only when the test is constructed conservatively.

### Clip-space intuition

A point transformed by the view-projection matrix becomes homogeneous clip coordinates:

```text
p_clip = ViewProjection * p_world
```

Before perspective divide, the canonical clipping conditions are expressed relative to `w`.

For the common Vulkan clip convention, after accounting for the exact projection convention used by this engine, visibility is ultimately related to inequalities of the form:

```text
-w <= x <= w
-w <= y <= w
z range according to Vulkan projection convention
```

After dividing by `w`, the point becomes NDC.

The important principle is that frustum culling asks whether an entire bound lies outside at least one clipping plane. If it does, the object can be rejected.

### Why GPU culling usually uses spheres/AABBs and not perfect tests

A perfect visibility test is not the goal. The goal is to spend much less time testing than drawing the rejected work would have cost.

GPU culling therefore values:

- few memory reads;
- low branch divergence;
- compact bounds;
- simple arithmetic;
- conservative results.

This explains why a slightly loose sphere can outperform a mathematically tighter but much more expensive bound test.

### Why Hi-Z works

A depth pyramid stores progressively coarser summaries of the depth buffer.

Conceptually:

```text
Mip 0: full-resolution depth
Mip 1: summary of 2x2 regions
Mip 2: summary of 4x4 regions
...
```

An object's screen-space rectangle can choose a mip where only a small number of samples approximate the depth of the entire covered region.

With reversed-Z, the reduction operation and comparison direction must match the engine's depth convention. Do not memorize “min” or “max” independent of that convention. Ask:

> Which numerical depth value represents the closest surface in this projection?

Then construct the pyramid so each texel conservatively represents the occluder information needed by the test.

### Temporal consequence

If culling uses the previous frame's depth pyramid, then visibility decisions are based on stale information. This can be acceptable because camera motion between adjacent frames is usually small, but the algorithm must remain conservative enough to avoid obvious popping.

Production systems may add:

- expanded bounds;
- velocity/camera-motion margins;
- one-frame visibility hysteresis;
- special handling for newly spawned objects;
- software/raster occlusion alternatives.

### Reasoning checkpoint

You should be able to answer:

1. Why culling prefers false positives over false negatives.
2. Why the cheapest valid bound is often better than the tightest bound.
3. Why reversed-Z changes how a depth pyramid is reduced/interpreted.
4. Why previous-frame occlusion introduces temporal error.
5. How you would measure whether Hi-Z saves more raster work than the culling pass itself costs.

# 19. Moving Chapter 5 frustum culling to the GPU

At this point compute generates the draw list, but it still emits one command for every object.

Now we can move the Chapter 5 CPU frustum test into the compute shader.

This is a useful first culling method because:

- you already have the bounds data;
- you already understand the CPU version;
- the result can be compared directly against Chapter 5;
- it avoids introducing a second new bounding representation while debugging GPU draw generation.

It is not the fastest possible culling test. We can optimize it later.

## The Chapter 5 idea

For every object, Chapter 5 transforms the eight corners of the local bounding box into clip space.

It finds the min/max NDC coordinates and rejects the object if the resulting box is completely outside the view.

We can use the same idea in compute.

Add this to `gpu_cull.comp`:

```glsl
bool is_visible(GPUObjectData object)
{
    const vec3 corners[8] = vec3[8](
        vec3( 1,  1,  1),
        vec3( 1,  1, -1),
        vec3( 1, -1,  1),
        vec3( 1, -1, -1),
        vec3(-1,  1,  1),
        vec3(-1,  1, -1),
        vec3(-1, -1,  1),
        vec3(-1, -1, -1)
    );

    mat4 matrix = sceneData.viewproj * object.transform;

    vec3 minNdc = vec3( 1.5);
    vec3 maxNdc = vec3(-1.5);

    for (uint i = 0; i < 8; ++i)
    {
        vec3 localPosition =
            object.boundsOriginRadius.xyz +
            corners[i] * object.boundsExtents.xyz;

        vec4 clip =
            matrix * vec4(localPosition, 1.0);

        // A production implementation should be more careful around
        // geometry crossing the camera plane. For now we keep this close
        // to the Chapter 5 test so the two paths can be compared.
        vec3 ndc = clip.xyz / clip.w;

        minNdc = min(minNdc, ndc);
        maxNdc = max(maxNdc, ndc);
    }

    if (minNdc.z > 1.0 || maxNdc.z < 0.0)
        return false;

    if (minNdc.x > 1.0 || maxNdc.x < -1.0)
        return false;

    if (minNdc.y > 1.0 || maxNdc.y < -1.0)
        return false;

    return true;
}
```

Then modify `main()`:

```glsl
void main()
{
    uint objectID = gl_GlobalInvocationID.x;

    if (objectID >= cull.objectCount)
        return;

    GPUObjectData object = cull.objects.objects[objectID];

    if (!is_visible(object))
        return;

    GPUMeshData mesh = cull.meshes.meshes[object.meshIndex];

    uint drawID = atomicAdd(cull.drawCount.count, 1);

    DrawIndexedIndirectCommand command;
    command.indexCount = mesh.indexCount;
    command.instanceCount = 1;
    command.firstIndex = mesh.firstIndex;
    command.vertexOffset = 0;
    command.firstInstance = objectID;

    cull.commands.commands[drawID] = command;
}
```

That is the core GPU-driven culling loop.

## Remove opaque CPU culling

Chapter 5 creates an `opaque_draws` array and filters it with `is_visible()`.

The GPU-driven opaque path no longer needs that CPU filter.

For opaque objects, upload the complete candidate list:

```cpp
uint32_t objectCount = upload_gpu_objects();
```

Then dispatch compute.

Keep the old CPU `is_visible()` function for transparent objects and debugging.

## A useful debug toggle

Add a simple boolean while developing:

```cpp
bool useGpuDrivenOpaque = true;
```

Then:

```cpp
if (useGpuDrivenOpaque)
{
    draw_gpu_driven_opaque(...);
}
else
{
    draw_chapter5_opaque(...);
}
```

Being able to switch between the two paths with the same camera is extremely useful when debugging disappearing geometry.

## Improving the culling test later

Eight corner transforms are not cheap.

Once everything works, common alternatives include:

- sphere/frustum plane tests;
- center/extents plane tests;
- cone culling for meshlets;
- projected bounding spheres;
- SIMD-friendly plane equations;
- hierarchical culling of scene nodes.

Do not optimize the culling formula until the GPU-driven pipeline is correct.

# 20. Integrating GPU culling into draw_geometry

We can now put the pieces together in the order they belong in a Vulkan 1.3 frame.

The important point for Dynamic Rendering is that **culling happens before `vkCmdBeginRendering()`**.

There is no reason to put compute inside the rendering scope.

A simplified `draw_geometry()` now has this shape:

```cpp
void VulkanEngine::draw_geometry(VkCommandBuffer cmd)
{
    FrameData& frame = get_current_frame();

    // --------------------------------------
    // Build scene descriptor, same idea as Chapter 5
    // --------------------------------------

    AllocatedBuffer gpuSceneDataBuffer = create_buffer(
        sizeof(GPUSceneData),
        VK_BUFFER_USAGE_UNIFORM_BUFFER_BIT,
        VMA_MEMORY_USAGE_CPU_TO_GPU);

        reinterpret_cast<GPUSceneData*>(
            gpuSceneDataBuffer.info.pMappedData);

    *sceneUniformData = sceneData;

    VkDescriptorSet globalDescriptor =
        frame._frameDescriptors.allocate(
            _device,
            _gpuSceneDataDescriptorLayout);

    DescriptorWriter writer;
    writer.write_buffer(
        0,
        gpuSceneDataBuffer.buffer,
        sizeof(GPUSceneData),
        0,
        VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER);
    writer.update_set(_device, globalDescriptor);

    frame._deletionQueue.push_function([=, this]() {
        destroy_buffer(gpuSceneDataBuffer);
    });

    // --------------------------------------
    // Upload candidate opaque objects
    // --------------------------------------

    uint32_t objectCount = upload_gpu_objects();

    // --------------------------------------
    // Reset count
    // --------------------------------------

    vkCmdFillBuffer(
        cmd,
        frame.gpuDrawCountBuffer.buffer,
        0,
        sizeof(uint32_t),
        0);

    // --------------------------------------
    // Compute visibility + command generation
    // --------------------------------------

            globalDescriptor,
            objectCount);
    }

    barrier_culling_to_indirect(cmd, frame);

    // --------------------------------------
    // Dynamic Rendering begins only now
    // --------------------------------------

    VkRenderingAttachmentInfo colorAttachment = /* existing code */;
    VkRenderingAttachmentInfo depthAttachment = /* existing code */;

    VkRenderingInfo renderInfo = /* existing code */;

    vkCmdBeginRendering(cmd, &renderInfo);

    // viewport/scissor
    // ...

    vkCmdEndRendering(cmd);

```

## `dispatch_gpu_culling()`

A helper keeps the draw function readable:

```cpp
void VulkanEngine::dispatch_gpu_culling(
    VkCommandBuffer cmd,
    VkDescriptorSet globalDescriptor,
    uint32_t objectCount)
{
    FrameData& frame = get_current_frame();

    vkCmdBindPipeline(
        cmd,
        VK_PIPELINE_BIND_POINT_COMPUTE,
        gpuDriven.cullPipeline);

    vkCmdBindDescriptorSets(
        cmd,
        VK_PIPELINE_BIND_POINT_COMPUTE,
        gpuDriven.cullPipelineLayout,
        0,
        1,
        &globalDescriptor,
        0,
        nullptr);

    GPUCullPushConstants push{};
    push.objectBuffer = frame.gpuObjectBufferAddress;
    push.meshBuffer = gpuDriven.meshBufferAddress;
    push.commandBuffer = frame.gpuIndirectBufferAddress;
    push.drawCountBuffer = frame.gpuDrawCountBufferAddress;
    push.objectCount = objectCount;

    vkCmdPushConstants(
        cmd,
        gpuDriven.cullPipelineLayout,
        VK_SHADER_STAGE_COMPUTE_BIT,
        0,
        sizeof(push),
        &push);

    uint32_t groups = (objectCount + 63) / 64;
    vkCmdDispatch(cmd, groups, 1, 1);
}
```

## `draw_gpu_driven_opaque()`

```cpp
void VulkanEngine::draw_gpu_driven_opaque(
    VkCommandBuffer cmd,
    VkDescriptorSet globalDescriptor,
    uint32_t objectCount)
{
    if (objectCount == 0)
        return;

    FrameData& frame = get_current_frame();

    vkCmdBindPipeline(
        cmd,
        VK_PIPELINE_BIND_POINT_GRAPHICS,
        gpuDriven.opaquePipeline.pipeline);

    VkDescriptorSet sets[] = {
        globalDescriptor,
        gpuDriven.bindlessTextureSet
    };

    vkCmdBindDescriptorSets(
        cmd,
        VK_PIPELINE_BIND_POINT_GRAPHICS,
        gpuDriven.opaquePipeline.layout,
        0,
        2,
        sets,
        0,
        nullptr);

    vkCmdBindIndexBuffer(
        cmd,
        gpuDriven.globalIndexBuffer.buffer,
        0,
        VK_INDEX_TYPE_UINT32);

    GPUDrivenDrawPushConstants push{};
    push.objectBuffer = frame.gpuObjectBufferAddress;
    push.meshBuffer = gpuDriven.meshBufferAddress;
    push.materialBuffer = gpuDriven.materialBufferAddress;

    vkCmdPushConstants(
        cmd,
        gpuDriven.opaquePipeline.layout,
        VK_SHADER_STAGE_VERTEX_BIT |
            VK_SHADER_STAGE_FRAGMENT_BIT,
        0,
        sizeof(push),
        &push);

    vkCmdDrawIndexedIndirectCount(
        cmd,
        frame.gpuIndirectBuffer.buffer,
        0,
        frame.gpuDrawCountBuffer.buffer,
        0,
        GPUDrivenRenderer::MaxObjects,
        sizeof(VkDrawIndexedIndirectCommand));
}
```

Notice that `objectCount` is only used to decide whether there can be work. The graphics call does not know the number of visible objects.

That number lives in `gpuDrawCountBuffer` and was produced by compute.

This is the point where the GPU decides how many opaque draws execute.

# 21. What to do with transparent objects

Do **not** immediately put transparent objects into the same compacted opaque indirect list.

Opaque rendering and transparent rendering have different constraints.

Opaque objects can usually be drawn in almost any order because the depth buffer resolves visibility.

Transparent blending normally requires approximate back-to-front ordering.

Chapter 5 already separates:

```cpp
DrawContext::OpaqueSurfaces
DrawContext::TransparentSurfaces
```

Keep that separation.

## First version: keep Chapter 5 transparent rendering

After the GPU-driven opaque draw, render transparent objects through the existing CPU path.

You can still CPU-cull them using the Chapter 5 `is_visible()` function.

A simplified helper is:

```cpp
void VulkanEngine::draw_transparent_cpu(
    VkCommandBuffer cmd,
    VkDescriptorSet globalDescriptor)
{
    MaterialPipeline* lastPipeline = nullptr;
    MaterialInstance* lastMaterial = nullptr;
    VkBuffer lastIndexBuffer = VK_NULL_HANDLE;

    for (const RenderObject& r : mainDrawContext.TransparentSurfaces)
    {
        if (!is_visible(r, sceneData.viewproj))
            continue;

        if (r.material != lastMaterial)
        {
            lastMaterial = r.material;

            if (r.material->pipeline != lastPipeline)
            {
                lastPipeline = r.material->pipeline;

                vkCmdBindPipeline(
                    cmd,
                    VK_PIPELINE_BIND_POINT_GRAPHICS,
                    lastPipeline->pipeline);

                vkCmdBindDescriptorSets(
                    cmd,
                    VK_PIPELINE_BIND_POINT_GRAPHICS,
                    lastPipeline->layout,
                    0,
                    1,
                    &globalDescriptor,
                    0,
                    nullptr);
            }

            vkCmdBindDescriptorSets(
                cmd,
                VK_PIPELINE_BIND_POINT_GRAPHICS,
                r.material->pipeline->layout,
                1,
                1,
                &r.material->materialSet,
                0,
                nullptr);
        }

        if (r.indexBuffer != lastIndexBuffer)
        {
            lastIndexBuffer = r.indexBuffer;
            vkCmdBindIndexBuffer(
                cmd,
                r.indexBuffer,
                0,
                VK_INDEX_TYPE_UINT32);
        }

        GPUDrawPushConstants push{};
        push.worldMatrix = r.transform;
        push.vertexBuffer = r.vertexBufferAddress;

        vkCmdPushConstants(
            cmd,
            r.material->pipeline->layout,
            VK_SHADER_STAGE_VERTEX_BIT,
            0,
            sizeof(push),
            &push);

        vkCmdDrawIndexed(
            cmd,
            r.indexCount,
            1,
            r.firstIndex,
            0,
            0);
    }
}
```

If you already added transparent depth sorting, keep it.

## Why this is not a failure of GPU-driven rendering

A good renderer does not have to make every category of geometry use the same submission path.

Typical render phases may have very different needs:

```text
Opaque            GPU-driven indirect
Alpha masked      GPU-driven indirect
Shadows           GPU-driven indirect
Transparent       CPU sorted or GPU sorted
Particles         specialized indirect path
UI                direct draws
```

The important thing is that the large opaque world—the part most likely to contain thousands or hundreds of thousands of objects—no longer requires one CPU draw command per object.

## Later: GPU-sorted transparency

If transparency becomes a bottleneck, you can generate transparent candidates on the GPU too and sort them by depth using:

- radix sort;
- bitonic sort for small lists;
- bucketed depth sorting;
- weighted blended OIT;
- per-material transparent lists.

That is a separate problem from basic GPU-driven opaque rendering, so we will not mix it into the first implementation.

# 22. Turning the transient draw list into a retained GPU scene

We now have GPU-generated visibility and draw commands, but there is still an important CPU cost:

```cpp
loadedScenes["structure"]->Draw(..., mainDrawContext);
```

still walks the scene graph every frame, and then:

```cpp
upload_gpu_objects();
```

copies every opaque object into this frame's object buffer.

That is a good **bridge architecture** because it lets us add GPU-driven rendering without rewriting scene management at the same time.

Once the renderer works, the next evolution is a retained GPU scene.

This corresponds to one of the most important ideas in the original GPU-driven VKGuide chapter: renderable objects should have persistent scene representation instead of being reconstructed only as immediate draw commands.

## What "retained" means

Instead of this:

```text
Every frame:
    scene graph -> RenderObject[] -> GPUObjectData[]
```

we want:

```text
When object is created:
    allocate stable GPU object ID

When object moves:
    mark that GPU object dirty

Every frame:
    upload only dirty object records

Compute:
    process the persistent object table
```

## A small retained scene structure

Start with:

```cpp
struct GPUSceneObject
{
    GPUObjectData data;
    bool dirty = true;
    bool active = true;
};

struct GPUScene
{
    std::vector<GPUSceneObject> objects;
    std::vector<uint32_t> dirtyObjects;

    uint32_t add_object(const GPUObjectData& data)
    {
        uint32_t index = static_cast<uint32_t>(objects.size());

        GPUSceneObject object{};
        object.data = data;
        object.dirty = true;
        object.active = true;

        objects.push_back(object);
        dirtyObjects.push_back(index);

        return index;
    }

    void update_object(
        uint32_t index,
        const GPUObjectData& data)
    {
        objects[index].data = data;

        if (!objects[index].dirty)
        {
            objects[index].dirty = true;
            dirtyObjects.push_back(index);
        }
    }
};
```

This is intentionally simple.

A production scene would need handles/generations, free lists, object removal, component integration, and thread-safe update queues. We do not need any of that to understand the rendering architecture.

## First retained-scene experiment: bake the static GLTF level

Your `structure.glb` level is a good first candidate because it is mostly static.

At load time, create a temporary `DrawContext` once:

```cpp
DrawContext bakedContext;
loadedScenes["structure"]->Draw(glm::mat4(1.0f), bakedContext);
```

Convert every opaque `RenderObject` to `GPUObjectData` and add it to the retained scene.

After that, stop adding the static structure GLTF to `mainDrawContext.OpaqueSurfaces` every frame.

Now the CPU no longer walks thousands of static mesh surfaces just to rediscover the same draw candidates.

Keep dynamic objects and transparent objects on the old path until you have a proper object-handle integration.

## Persistent object buffer

Once objects are retained, the object buffer no longer needs to be completely rewritten each frame.

You have two straightforward choices.

### Option A — one object buffer per frame in flight

This is easiest to synchronize.

Each frame owns a complete copy of `GPUObjectData[]`.

When an object becomes dirty, make sure its new value eventually reaches every frame copy.

You can keep a version number per object and per frame.

### Option B — one device-local persistent object buffer

Upload dirty ranges through staging/transfer commands.

This reduces duplication and gives better GPU memory placement, but you must synchronize transfer writes against culling reads.

For your first engine, **Option A is simpler**.

The object table is relatively small compared with textures and geometry.

For example, 100,000 objects at 112 bytes each is about 10.7 MiB per frame copy.

That is acceptable while learning the architecture.

## Dirty upload helper

With a per-frame mapped object table:

```cpp
void VulkanEngine::upload_dirty_scene_objects(FrameData& frame)
{
    auto* destination =
        reinterpret_cast<GPUObjectData*>(
            frame.gpuObjectBuffer.info.pMappedData);

    for (uint32_t objectIndex : gpuScene.dirtyObjects)
    {
        destination[objectIndex] =
            gpuScene.objects[objectIndex].data;
    }

    // For non-coherent memory, either flush each merged dirty range
    // or flush the used object-buffer range here.
}
```

Do not clear a global dirty bit after updating only one frame copy unless the other frame copies have also received the change.

A common solution is object versions:

```cpp
struct GPUSceneObject
{
    GPUObjectData data;
    uint64_t version = 0;
};
```

and each frame remembers the latest uploaded version.

This is engine architecture rather than Vulkan API mechanics, so implement it only when the transient bridge becomes a measurable CPU cost.

## Candidate lists

Once the scene is retained, you do not necessarily want compute to scan every object for every render phase.

You can maintain lists such as:

```text
opaque candidates
alpha-mask candidates
shadow candidates
transparent candidates
```

Those candidate lists contain stable object IDs.

The culling shader reads an object ID from the candidate list instead of assuming:

```glsl
objectID = gl_GlobalInvocationID.x;
```

This becomes useful when an object belongs to some phases but not others.

For the current tutorial, scanning the opaque object table directly is enough.

# 23. Adding a depth pyramid

Frustum culling rejects objects outside the camera view, but it still draws objects hidden behind walls or other large geometry.

To reject those, we need an approximate GPU-readable representation of the depth buffer.

A common solution is a hierarchical Z buffer, often called **Hi-Z** or a **depth pyramid**.

The idea is:

```text
full-resolution depth
        |
        v
mip 0: 1920 x 1080
mip 1:  960 x 540
mip 2:  480 x 270
mip 3:  240 x 135
...
```

Each lower-resolution texel represents a region of the higher-resolution image.

The culling shader projects an object's bounds to the screen and chooses a mip level where that rectangle covers only a small number of texels.

It can then estimate whether the object is completely behind previously rendered geometry.

## Use the previous frame first

There are several possible pipelines:

```text
Depth prepass
    -> build current Hi-Z
    -> cull
    -> main draw
```

or:

```text
Previous frame Hi-Z
    -> cull current frame
    -> main draw
    -> build next Hi-Z
```

For this tutorial, use the **previous frame's pyramid**.

It fits naturally into the renderer we already have:

```text
Frame N:
    cull using pyramid from N-1
    render frame N
    build pyramid N
```

The tradeoff is that rapidly moving cameras or objects can make the old depth conservative/inaccurate. We will use a bias and can disable occlusion for problematic cases.

A production renderer can add reprojection or a depth prepass later.

## Create the pyramid image

Use a float format that supports sampling and storage-image writes, for example:

```cpp
VK_FORMAT_R32_SFLOAT
```

Calculate the mip count:

```cpp
uint32_t calculate_mip_count(VkExtent2D extent)
{
    return uint32_t(std::floor(std::log2(
        std::max(extent.width, extent.height)))) + 1;
}
```

Create an image with:

```cpp
VK_IMAGE_USAGE_SAMPLED_BIT |
VK_IMAGE_USAGE_STORAGE_BIT
```

and all mip levels.

You will also want:

- one image view covering the whole pyramid for sampling;
- one image view per mip for storage-image output.

The current `AllocatedImage` helper only needs a small extension to support custom mip views.

Store something like:

```cpp
struct DepthPyramid
{
    AllocatedImage image;
    VkImageView fullView = VK_NULL_HANDLE;
    std::vector<VkImageView> mipViews;
    uint32_t mipLevels = 0;
    VkSampler sampler = VK_NULL_HANDLE;
};
```

Because the swapchain/draw extent can change, recreate this resource when the draw extent changes.

## Build it after Dynamic Rendering ends

At the end of geometry rendering:

```cpp
vkCmdEndRendering(cmd);
```

Now the depth attachment contains this frame's depth.

Transition the depth image for shader sampling.

With Sync2, the relevant dependency is conceptually:

```text
EARLY/LATE_FRAGMENT_TESTS
DEPTH_STENCIL_ATTACHMENT_WRITE
        ->
COMPUTE_SHADER
SHADER_SAMPLED_READ
```

For example:

```cpp
VkImageMemoryBarrier2 depthBarrier{};
depthBarrier.sType = VK_STRUCTURE_TYPE_IMAGE_MEMORY_BARRIER_2;

depthBarrier.srcStageMask =
    VK_PIPELINE_STAGE_2_EARLY_FRAGMENT_TESTS_BIT |
    VK_PIPELINE_STAGE_2_LATE_FRAGMENT_TESTS_BIT;

depthBarrier.srcAccessMask =
    VK_ACCESS_2_DEPTH_STENCIL_ATTACHMENT_WRITE_BIT;

depthBarrier.dstStageMask =
    VK_PIPELINE_STAGE_2_COMPUTE_SHADER_BIT;

depthBarrier.dstAccessMask =
    VK_ACCESS_2_SHADER_SAMPLED_READ_BIT;

depthBarrier.oldLayout =
    VK_IMAGE_LAYOUT_DEPTH_ATTACHMENT_OPTIMAL;

depthBarrier.newLayout =
    VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL;

depthBarrier.image = _depthImage.image;
depthBarrier.subresourceRange.aspectMask = VK_IMAGE_ASPECT_DEPTH_BIT;
depthBarrier.subresourceRange.baseMipLevel = 0;
depthBarrier.subresourceRange.levelCount = 1;
depthBarrier.subresourceRange.baseArrayLayer = 0;
depthBarrier.subresourceRange.layerCount = 1;
```

Submit it through `vkCmdPipelineBarrier2()`.

Before the next frame uses `_depthImage` as a depth attachment again, transition it back to `VK_IMAGE_LAYOUT_DEPTH_ATTACHMENT_OPTIMAL` as part of your normal attachment preparation.

## Pyramid reduction shader

The first stage copies/reduces the hardware depth image into pyramid mip 0.

Later stages reduce mip N into mip N+1.

Because VKGuide uses **reversed-Z**, near values are larger and far values are smaller.

For conservative occlusion, each pyramid texel should contain the **minimum** depth from the region it represents.

Why minimum?

Suppose one 2x2 source region contains:

```text
0.90  0.88
0.91  0.20
```

With reversed-Z, `0.20` is the farthest depth in that group.

If we store `0.20`, then an object can only be declared occluded when it is behind even that farthest sample. That makes the test conservative.

A reduction shader for a pyramid mip can look like:

```glsl
#version 460

layout(local_size_x = 8, local_size_y = 8) in;

layout(set = 0, binding = 0) uniform sampler2D sourceDepth;
layout(set = 0, binding = 1, r32f) uniform writeonly image2D destinationMip;

void main()
{
    ivec2 dst = ivec2(gl_GlobalInvocationID.xy);
    ivec2 dstSize = imageSize(destinationMip);

    if (dst.x >= dstSize.x || dst.y >= dstSize.y)
        return;

    ivec2 srcBase = dst * 2;
    ivec2 srcSize = textureSize(sourceDepth, 0);

    ivec2 p0 = min(srcBase + ivec2(0, 0), srcSize - 1);
    ivec2 p1 = min(srcBase + ivec2(1, 0), srcSize - 1);
    ivec2 p2 = min(srcBase + ivec2(0, 1), srcSize - 1);
    ivec2 p3 = min(srcBase + ivec2(1, 1), srcSize - 1);

    float d0 = texelFetch(sourceDepth, p0, 0).r;
    float d1 = texelFetch(sourceDepth, p1, 0).r;
    float d2 = texelFetch(sourceDepth, p2, 0).r;
    float d3 = texelFetch(sourceDepth, p3, 0).r;

    float farthestDepth = min(min(d0, d1), min(d2, d3));

    imageStore(destinationMip, dst, vec4(farthestDepth));
}
```

For mip 0, you can either:

1. use a small copy shader that reads one hardware depth texel per output texel; or
2. treat the hardware depth as the "source level" and have mip 0 already be half resolution.

Option 1 is easier to reason about because mip 0 matches the render extent.

## Compute-to-compute barriers between mips

After writing one pyramid mip, the next dispatch samples it.

Add a Sync2 image barrier between dispatches:

```text
COMPUTE_SHADER / SHADER_STORAGE_WRITE
        ->
COMPUTE_SHADER / SHADER_SAMPLED_READ
```

Keep the pyramid image in `VK_IMAGE_LAYOUT_GENERAL` while building it if that makes your descriptor setup simpler.

Once the full chain is generated, transition it to `VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL` for next frame's culling pass.

## First checkpoint: visualize the pyramid

Before using it for culling, render one selected mip to ImGui or the draw image.

You should see a coarse depth representation of the scene.

Do this before allowing the pyramid to make visibility decisions. A broken Hi-Z image can make the entire scene vanish and is harder to debug from culling symptoms alone.

# 24. Occlusion culling with reversed-Z

Once the depth pyramid is valid, the culling shader can reject hidden objects.

The workflow is:

```text
Object bounds
    |
    v
project to screen
    |
    v
screen-space rectangle
    |
    v
choose Hi-Z mip
    |
    v
sample conservative depth
    |
    v
visible / occluded
```

## Add the pyramid to the culling pipeline

The culling compute pipeline currently uses:

```text
set 0 = GPUSceneData
```

Add a second descriptor set or a second binding containing the previous frame's depth pyramid.

A simple layout is:

```glsl
layout(set = 1, binding = 0)
uniform sampler2D depthPyramid;
```

Then the cull pipeline layout becomes:

```text
set 0 = scene data
set 1 = depth pyramid
```

You can allocate one descriptor set per frame because every frame owns/produces its own pyramid.

## Get the screen rectangle

Our frustum culling loop already transforms all eight bounding-box corners.

While doing that, keep:

```glsl
vec3 minNdc;
vec3 maxNdc;
```

The XY range converts to UV space with:

```glsl
vec2 minUV = minNdc.xy * 0.5 + 0.5;
vec2 maxUV = maxNdc.xy * 0.5 + 0.5;
```

Clamp it:

```glsl
minUV = clamp(minUV, vec2(0.0), vec2(1.0));
maxUV = clamp(maxUV, vec2(0.0), vec2(1.0));
```

The projected size in pixels is:

```glsl
vec2 pyramidSize = vec2(textureSize(depthPyramid, 0));
vec2 rectPixels = (maxUV - minUV) * pyramidSize;
```

Choose a mip roughly matching the largest dimension:

```glsl
float maxDimension = max(rectPixels.x, rectPixels.y);
float mip = ceil(log2(max(maxDimension, 1.0)));
```

Clamp against the number of levels.

## Which object depth do we compare?

With reversed-Z:

```text
larger depth = closer
smaller depth = farther
```

For an object's eight corners:

```glsl
maxNdc.z
```

is the closest depth among the corners.

If even the object's **closest** point is behind the conservative occluder depth, the object is hidden.

Sample the chosen mip at the rectangle corners:

```glsl
float d0 = textureLod(depthPyramid, minUV, mip).r;
float d1 = textureLod(depthPyramid, vec2(maxUV.x, minUV.y), mip).r;
float d2 = textureLod(depthPyramid, vec2(minUV.x, maxUV.y), mip).r;
float d3 = textureLod(depthPyramid, maxUV, mip).r;

float occluderDepth = min(min(d0, d1), min(d2, d3));
```

Again, minimum is conservative for reversed-Z.

Then:

```glsl
float objectNearestDepth = maxNdc.z;

bool occluded =
    objectNearestDepth < occluderDepth - depthBias;
```

If `occluded`, return before writing an indirect command.

## Start with a generous bias

Previous-frame occlusion is not perfect.

Use a small bias and prefer false positives in visibility over false negatives.

A false positive means:

```text
we draw an object that was actually hidden
```

That only costs performance.

A false negative means:

```text
we fail to draw a visible object
```

That creates obvious popping and holes.

Be conservative.

## Camera motion problem

The previous frame's depth pyramid describes the previous frame's camera.

If the camera rotates quickly, a region that was occluded previously may now be visible.

Simple solutions while learning include:

- disable occlusion when camera movement exceeds a threshold;
- enlarge projected bounds;
- use a larger depth bias;
- treat recently invisible objects as visible for one frame;
- only use Hi-Z for large objects initially.

More advanced engines reproject depth or run a current-frame depth prepass.

Do not let this complexity block the first implementation.

## Culling function shape

By now your compute shader can conceptually look like:

```glsl
void main()
{
    uint objectID = gl_GlobalInvocationID.x;

    if (objectID >= cull.objectCount)
        return;

    GPUObjectData object = cull.objects.objects[objectID];

    ProjectedBounds bounds = project_bounds(object);

    if (!bounds.inFrustum)
        return;

    if (occlusionEnabled &&
        is_occluded(bounds, depthPyramid))
    {
        return;
    }

    GPUMeshData mesh = cull.meshes.meshes[object.meshIndex];

    uint drawID = atomicAdd(cull.drawCount.count, 1);

    cull.commands.commands[drawID] =
        make_draw(mesh, objectID);
}
```

That is the core of a modern GPU-generated visible draw list.

# 25. GPU-driven shadow rendering

Chapter 5 does not include a shadow-map system, so treat this section as the first extension after the main GPU-driven renderer works.

The useful idea is that shadows do **not** require a second scene representation.

The same:

```text
GPUObjectData[]
GPUMeshData[]
global index buffer
```

can feed another culling pass and another indirect list.

The difference is the camera used for culling and the pipeline used for drawing.

## A separate draw list

Camera visibility and light visibility are different.

Add another command/count pair, for example:

```cpp
AllocatedBuffer shadowIndirectBuffer;
VkDeviceAddress shadowIndirectBufferAddress;

AllocatedBuffer shadowDrawCountBuffer;
VkDeviceAddress shadowDrawCountBufferAddress;
```

These can also be per-frame.

Dispatch the same culling shader with a different view-projection matrix, or create a small shadow-culling variant.

The output commands have the same `VkDrawIndexedIndirectCommand` format.

## Depth-only Dynamic Rendering

A shadow map is a good example of why render phases remain useful even though `VkRenderPass` is gone.

Create a depth image and transition it to:

```cpp
VK_IMAGE_LAYOUT_DEPTH_ATTACHMENT_OPTIMAL
```

Then begin Dynamic Rendering with **zero color attachments**:

```cpp
VkRenderingAttachmentInfo depthAttachment{};
depthAttachment.sType =
    VK_STRUCTURE_TYPE_RENDERING_ATTACHMENT_INFO;
depthAttachment.imageView = shadowImage.imageView;
depthAttachment.imageLayout =
    VK_IMAGE_LAYOUT_DEPTH_ATTACHMENT_OPTIMAL;
depthAttachment.loadOp = VK_ATTACHMENT_LOAD_OP_CLEAR;
depthAttachment.storeOp = VK_ATTACHMENT_STORE_OP_STORE;
depthAttachment.clearValue.depthStencil.depth = 0.0f;

VkRenderingInfo renderingInfo{};
renderingInfo.sType = VK_STRUCTURE_TYPE_RENDERING_INFO;
renderingInfo.renderArea.offset = { 0, 0 };
renderingInfo.renderArea.extent = shadowExtent;
renderingInfo.layerCount = 1;
renderingInfo.colorAttachmentCount = 0;
renderingInfo.pColorAttachments = nullptr;
renderingInfo.pDepthAttachment = &depthAttachment;

vkCmdBeginRendering(cmd, &renderingInfo);
```

The clear value above assumes you keep the same reversed-Z convention for the shadow projection. If you use conventional depth for the shadow map, use the corresponding compare operation and clear value instead.

Bind a depth-only graphics pipeline, the global index buffer, and the object/mesh tables.

Then:

```cpp
vkCmdDrawIndexedIndirectCount(
    cmd,
    frame.shadowIndirectBuffer.buffer,
    0,
    frame.shadowDrawCountBuffer.buffer,
    0,
    GPUDrivenRenderer::MaxObjects,
    sizeof(VkDrawIndexedIndirectCommand));
```

Finally:

```cpp
vkCmdEndRendering(cmd);
```

Transition the shadow image for shader sampling before the main lighting pass.

## Alpha-masked materials

Depth-only vertex rendering works for fully opaque objects.

Alpha-masked foliage needs a fragment shader that samples the base-color alpha and discards pixels below the cutoff.

Because we already have:

```text
materialIndex
bindless texture table
```

we can use the same GPU material data in the shadow fragment shader.

This is a good example of why converting materials into GPU-readable data pays off beyond the main color pass.

# 26. Frames in flight and resource ownership

GPU-driven rendering adds more buffers, but the lifetime rules are the same Vulkan rules you have already been using.

The most important distinction is between **persistent asset data** and **per-frame generated data**.

## Persistent resources

These can be shared across frames:

```text
globalIndexBuffer
meshBuffer
materialBuffer
bindlessTextureLayout
bindlessTextureSet
opaque graphics pipeline
cull compute pipeline
```

They only change when assets/scenes are registered.

## Per-frame resources

These are written every frame and must not be reused while the GPU is still using them:

```text
gpuObjectBuffer
gpuIndirectBuffer
gpuDrawCountBuffer
shadow indirect/count buffers
per-frame scene UBO
per-frame depth pyramid, if using that ownership model
```

Putting them in `FrameData` naturally follows the same fence-based frame reuse that VKGuide already has.

## Do not share one indirect buffer between in-flight frames

Suppose frame 0's compute shader writes:

```text
indirectBuffer
```

and the CPU immediately starts frame 1 and records a reset/write to the same buffer.

The GPU may still be executing frame 0.

That creates a race.

One command/count pair per `FrameData` removes that problem.

## Bindless resource lifetime

Our first bindless implementation assumes texture registration happens during asset loading, before active frames use the descriptor entry.

There is another lifetime issue when unloading GLTF assets.

`LoadedGLTF::clearAll()` destroys its images and samplers. The global bindless table may still contain descriptors referring to those resources.

For this tutorial, use the same simple lifetime model as the example level:

> Do not unload a GLTF asset while its bindless resources are registered and potentially usable by the renderer.

A production system should add a texture registry with:

- reference counts or handles;
- descriptor-slot reuse;
- replacement with a default descriptor before destruction;
- deferred destruction after all in-flight frames finish;
- generation numbers to catch stale handles.

This is an asset-system problem, which is why the legacy GPU-driven guide's material architecture became intertwined with its Extra Chapter.

We deliberately avoided requiring that system here.

## Reading the GPU draw count for statistics

After compute culling, the CPU no longer knows the visible draw count without a readback.

Do not map the GPU count buffer and wait on it every frame. That would introduce the exact CPU/GPU synchronization stall we are trying to avoid.

If you want the visible count in your ImGui statistics window:

1. create a small GPU-to-CPU readback buffer per frame;
2. after the indirect draw is finished, copy the count into it;
3. read it only when that `FrameData` fence is waited on the next time the frame slot is reused.

The displayed value may be a couple of frames old. That is perfectly fine for debug statistics.

Conceptually:

```cpp
vkCmdCopyBuffer(
    cmd,
    frame.gpuDrawCountBuffer.buffer,
    frame.drawCountReadback.buffer,
    1,
    &copy);
```

Add the appropriate indirect/compute → transfer-read dependency before the copy.

Then, after waiting for this frame slot's fence on a future CPU frame:

```cpp
uint32_t visibleDraws =
    *reinterpret_cast<uint32_t*>(
        frame.drawCountReadback.info.pMappedData);
```

You can add:

```cpp
stats.visible_gpu_draws = visibleDraws;
```

without stalling the current GPU work.

# 27. Final frame flow

After all the pieces are implemented, a frame can look like this.

The exact image-transition code depends on the current state of your VKGuide checkout, so keep the transition helpers you already have. Focus on the ordering.

```cpp
void VulkanEngine::draw_geometry(VkCommandBuffer cmd)
{
    FrameData& frame = get_current_frame();

    // -------------------------------------------------
    // 1. Prepare this frame's CPU-visible scene data
    // -------------------------------------------------

    VkDescriptorSet globalDescriptor =
        create_scene_descriptor_for_this_frame();

    // Bridge version: rebuild from DrawContext.
    // Retained version: upload only dirty objects.
    uint32_t objectCount = upload_gpu_objects();

    // -------------------------------------------------
    // 2. Reset GPU-generated draw count
    // -------------------------------------------------

    vkCmdFillBuffer(
        cmd,
        frame.gpuDrawCountBuffer.buffer,
        0,
        sizeof(uint32_t),
        0);

    barrier_count_reset_to_compute(cmd, frame);

    // -------------------------------------------------
    // 3. GPU culling + indirect-command generation
    // -------------------------------------------------

    if (objectCount > 0)
    {
        dispatch_gpu_culling(
            cmd,
            globalDescriptor,
            objectCount);
    }

    barrier_culling_to_indirect(cmd, frame);

    // -------------------------------------------------
    // 4. Prepare Dynamic Rendering attachments
    // -------------------------------------------------

    // Use your existing Sync2 image-transition helpers.
    transition_draw_image_to_color_attachment(cmd);
    transition_depth_image_to_depth_attachment(cmd);

    VkRenderingAttachmentInfo colorAttachment =
        make_color_attachment();

    VkRenderingAttachmentInfo depthAttachment =
        make_depth_attachment();

    VkRenderingInfo renderInfo =
        make_rendering_info(colorAttachment, depthAttachment);

    // -------------------------------------------------
    // 5. Dynamic Rendering
    // -------------------------------------------------

    vkCmdBeginRendering(cmd, &renderInfo);

    set_main_viewport_and_scissor(cmd);

    // GPU-driven opaque world
    draw_gpu_driven_opaque(
        cmd,
        globalDescriptor,
        objectCount);

    // Existing Chapter 5 path for transparent objects
    draw_transparent_cpu(
        cmd,
        globalDescriptor);

    vkCmdEndRendering(cmd);

    // -------------------------------------------------
    // 6. Build depth pyramid for future culling
    // -------------------------------------------------

    transition_depth_attachment_to_compute_read(cmd);
    build_depth_pyramid(cmd);

    // -------------------------------------------------
    // 7. Continue the Chapter 5 frame
    // -------------------------------------------------

    // draw image -> swapchain/composite
    // ImGui
    // present transitions
    // ...
}
```

The architecture is now:

```text
CPU
 |
 | scene changes / candidate objects
 v
GPUObjectData[]
 |
 v
Compute Culling
 |       |
 |       +----------------------+
 |                              |
 v                              v
Indirect Commands          Draw Count
 |                              |
 +--------------+---------------+
                |
                v
      Draw-Indirect stage
                |
                v
      Dynamic Rendering
                |
     +----------+----------+
     |                     |
     v                     v
GPU opaque          CPU transparent
     |
     v
Depth Buffer
     |
     v
Depth Pyramid
     |
     +---- used by future culling
```

## What happened to render passes?

Nothing.

We never needed them.

Your engine already uses Dynamic Rendering, so the GPU-driven work simply runs before and between `vkCmdBeginRendering()` / `vkCmdEndRendering()` regions.

The engine can still have conceptual render phases:

```text
Shadow
Opaque
Transparent
Post Process
UI
```

but those phases do not need `VkRenderPass` objects.

# 28. Debugging and validation checklist

GPU-driven bugs often produce a black screen instead of a friendly error. Work through them systematically.

## Indirect draw does nothing

Check the indirect buffer usage:

```cpp
VK_BUFFER_USAGE_INDIRECT_BUFFER_BIT
```

Check the count buffer usage too:

```cpp
VK_BUFFER_USAGE_INDIRECT_BUFFER_BIT
```

Check that `drawIndirectCount`, `multiDrawIndirect`, and `drawIndirectFirstInstance` were enabled.

Make sure:

```cpp
stride == sizeof(VkDrawIndexedIndirectCommand)
```

and the indirect offset is aligned as required.

## Validation says the first instance is invalid

Make sure:

```cpp
baseFeatures.drawIndirectFirstInstance = VK_TRUE;
```

was actually enabled on device creation.

## All objects use the wrong transform

Check compute:

```cpp
command.firstInstance = objectID;
```

and vertex shader:

```glsl
uint objectID = gl_InstanceIndex;
```

Also check that `instanceCount` is 1.

## Geometry explodes

First render only one object.

Check:

```text
sourceFirstIndex
copy byte offsets
destinationFirstIndex
GPUMeshData.firstIndex
VkDrawIndexedIndirectCommand.firstIndex
```

Remember:

```text
firstIndex is measured in indices
VkBufferCopy offsets are measured in bytes
```

The conversion is:

```cpp
VkDeviceSize byteOffset =
    VkDeviceSize(firstIndex) * sizeof(uint32_t);
```

## Some surfaces use another surface's vertices

Check `GPUMeshData.vertexBufferAddress`.

Every registered `GeoSurface` of the same `MeshAsset` can share the same vertex address, but surfaces from different mesh assets should point to the correct mesh vertex buffer.

## Textures become random

Check that the shader has:

```glsl
#extension GL_EXT_nonuniform_qualifier : require
```

and uses:

```glsl
textures[nonuniformEXT(material.colorTexture)]
```

Check CPU/GLSL `GPUMaterialData` layout.

Check that the descriptor array was completely initialized.

Check that the image is still alive.

## Culling removes objects that should be visible

Disable occlusion first.

If the problem remains, disable frustum culling by replacing:

```glsl
if (!is_visible(object))
    return;
```

with no test.

If all geometry reappears, visualize/debug the projected bounds.

Start by comparing one object against Chapter 5's CPU `is_visible()` result.

## Objects behind the camera generate NaNs

The simple eight-corner tutorial test divides by `clip.w` and intentionally mirrors Chapter 5 closely.

Geometry intersecting the camera plane can make this less robust.

Once the architecture works, replace it with a proper frustum-plane test or handle non-positive `w` conservatively by treating the object as visible.

Never aggressively cull uncertain objects.

## Compute appears to run, but draw count stays zero

Temporarily remove culling.

Then verify the reset/compute barrier:

```text
TRANSFER_WRITE
    ->
COMPUTE_SHADER / SHADER_READ|WRITE
```

Verify that the buffer device address pushed to compute is the address of the **current frame's** count buffer.

## Compute writes commands, but graphics sees old commands

Check the compute → indirect barrier:

```text
srcStage  = COMPUTE_SHADER
srcAccess = SHADER_WRITE

dstStage  = DRAW_INDIRECT
dstAccess = INDIRECT_COMMAND_READ
```

Both command and count buffers need the dependency.

## Descriptor layout validation errors after adding compute

The existing scene UBO binding needs:

```cpp
VK_SHADER_STAGE_COMPUTE_BIT
```

in its descriptor-set-layout stage flags if the cull shader accesses it.

## Black screen only in the new graphics pipeline

Use the CPU-generated multi-draw checkpoint again.

If CPU-generated indirect works but compute-generated indirect does not, the graphics pipeline is probably fine and the issue is compute or synchronization.

This is exactly why we built the tutorial in checkpoints.

# 29. What we deliberately did not add yet

A modern GPU-driven renderer can become much more complicated than the system we just built.

The following features are useful, but none are required to understand or benefit from the architecture.

## Descriptor buffers / descriptor heaps

Vulkan has newer descriptor models than descriptor indexing.

They can reduce descriptor-management overhead and fit very large engines well.

But Chapter 5 already teaches descriptor sets, and descriptor indexing is enough to build a fully functional bindless GPU-driven renderer.

Keep the engine's resource handles abstract enough that you can replace the backend later.

## Mesh shaders

Mesh shaders are a natural future step for GPU-driven rendering, especially when you move from whole-mesh culling to meshlet culling.

But they are not necessary.

The combination of:

```text
compute culling
+
indexed multi-draw indirect
+
bindless materials
```

is already powerful and works on a broader set of Vulkan hardware.

## Meshlets

We currently cull one `GeoSurface` at a time.

Large meshes can still waste GPU work if only a small part of the surface is visible.

Meshlets split geometry into small clusters with their own bounds.

Later your hierarchy can become:

```text
Object
  -> mesh
      -> meshlet
```

and the GPU can cull at a much finer granularity.

## GPU LOD selection

This is an excellent next improvement.

Change the mesh record so an object references a mesh asset containing multiple LOD ranges:

```cpp
struct GPUMeshLOD
{
    uint32_t firstIndex;
    uint32_t indexCount;
};

struct GPUMeshData
{
    VkDeviceAddress vertexBufferAddress;
    GPUMeshLOD lods[4];
    uint32_t lodCount;
};
```

The culling shader estimates projected size and chooses the indirect command's index range.

Now LOD selection costs no per-object CPU work.

## GPU sorting

Our compacted output order depends on atomic execution order and should be considered unspecified.

Opaque rendering still works, but it may not be optimal for cache behavior.

A more advanced renderer can build sort keys containing:

```text
pipeline/material class
mesh
LOD
depth bucket
```

and GPU-sort the visible list before emitting draws.

For the simple bindless pipeline in this chapter, sorting is not necessary for correctness.

## Async compute

Culling can potentially run on a compute queue, but that introduces queue-family/ownership and semaphore scheduling questions.

Do not move it to async compute until profiling shows a reason.

One graphics queue with:

```text
compute -> barrier -> graphics
```

is an excellent first architecture and is much easier to debug.

## Timeline semaphores

Timeline semaphores are very useful once you have multiple queues, background uploads, or more complicated scheduling.

They are not needed for the single-queue frame graph built here.

# 30. Where to go next

At this point you have the foundation needed for a much more serious renderer.

For the engine path you are following, I would continue in this order.

## 1. Make the opaque path completely stable

Before adding another rendering feature, test:

- large GLTF scenes;
- multiple GLTF files loaded together;
- many materials;
- moving objects;
- camera movement;
- resize handling;
- validation layers;
- RenderDoc captures.

Make sure switching between CPU opaque rendering and GPU opaque rendering produces the same scene.

## 2. Improve the retained GPU scene

Move static scene objects out of the per-frame `DrawContext` rebuild.

Give renderable objects stable handles and update only dirty transforms/materials.

This is the step that reduces CPU scene-processing overhead in addition to draw-call overhead.

## 3. Add GPU LOD selection

You already have the compute stage deciding whether a mesh is drawn.

Choosing which LOD to draw is a small extension to the same decision.

## 4. Finish Hi-Z occlusion

Add debugging views and conservative handling for moving cameras/objects.

Measure how many objects frustum culling rejects versus how many Hi-Z rejects.

## 5. Add a shadow phase

Reuse the same scene tables and generate a light-visible indirect list.

This reinforces the idea that `GPUObjectData[]` is the central render-scene representation, while draw lists are temporary products generated for different phases.

## 6. Add skeletal meshes

Do not create a completely unrelated renderer for animated meshes.

A skinned object should still have:

```text
object ID
mesh ID
material ID
bounds
```

The difference is where its final vertex positions come from.

A straightforward progression is:

```text
CPU animation pose
    -> bone matrix buffer
    -> vertex shader skinning
```

Later:

```text
bone matrices
    -> compute skinning
    -> skinned vertex buffer
    -> same GPU-driven draw path
```

The culling/draw-command architecture does not need to be replaced.

For animated characters, update bounds conservatively or use animation-aware bounds.

## 7. Integrate physics independently

When you later integrate Jolt, keep simulation and rendering representation separate.

Physics updates object transforms.

Those transforms mark GPU scene objects dirty.

The rendering system does not need to know whether a transform came from:

- Jolt;
- animation;
- gameplay;
- an editor gizmo;
- networking.

That separation will make the engine much easier to evolve.

## 8. Only then investigate meshlets / mesh shaders

At that point you will understand exactly which part of your renderer they replace and what problem they solve.

That is much more useful than starting with mesh shaders before understanding indirect rendering and GPU scene management.

```text
gpu_mesh.vert
gpu_mesh.frag
gpu_cull.comp
```

Later for Hi-Z:

```text
depth_copy.comp
depth_reduce.comp
```

If you add shadows:

```text
gpu_shadow.vert
```

and optionally an alpha-mask shadow fragment shader.

## Shader compile script

Add the new shaders to the same shader compilation script used by VKGuide.

For a `glslc` setup, the commands are conceptually:

```bash
glslc gpu_mesh.vert -o gpu_mesh.vert.spv
glslc gpu_mesh.frag -o gpu_mesh.frag.spv
glslc gpu_cull.comp -o gpu_cull.comp.spv
```

Use the same include paths/output folder as the existing `mesh.vert` and `mesh.frag` compilation commands in your project.

## Cleanup

Destroy:

```text
global index buffer
mesh table buffer
material table buffer
bindless descriptor pool
bindless descriptor-set layout
GPU-driven graphics pipeline/layout
culling compute pipeline/layout
per-frame object/indirect/count buffers
depth pyramid views/images/samplers, if added
```

Make sure the device is no longer using them when they are destroyed, following the same fence/deletion-queue patterns from the earlier chapters.

# 32. Final architecture recap

We started Chapter 6 with a Chapter 5 `RenderObject` that directly described one CPU-recorded draw:

```text
RenderObject
    material pointer
    index VkBuffer
    vertex address
    transform
        |
        v
vkCmdDrawIndexed
```

We evolved it into a GPU scene:

```text
                         CPU / Asset Loading

                +-----------------------------+
                |                             |
                v                             v
         GPUMeshData[]                GPUMaterialData[]
                |                             |
                |                     bindless textures[]
                |                             |
                +-------------+---------------+
                              |
                              v
                       GPUObjectData[]
                              |
                              v
                    Compute Visibility
                   /         |          \
                  /          |           \
             frustum        Hi-Z         LOD
                  \          |           /
                   \         |          /
                    +--------+---------+
                             |
                             v
             VkDrawIndexedIndirectCommand[]
                             +
                         drawCount
                             |
                             v
                 Synchronization2 barrier
                             |
                             v
                 Dynamic Rendering begins
                             |
                             v
              bind one global index buffer
              bind one bindless texture set
              push GPU table addresses
                             |
                             v
             vkCmdDrawIndexedIndirectCount
                             |
                             v
                    opaque scene rendered
```

The CPU is now responsible for high-level scene changes and resource management.

The GPU is responsible for deciding which opaque objects turn into actual graphics work.

That is the central transition the GPU Driven Rendering chapter is trying to teach.
